# HANDOFF

## 1. 这个程序在做什么（≤5 行）

- 读 `argv[2]` 的 JSON（`{courses:[], ops:[]}`），把 `ops` 按顺序施加在 `courses` 的**深拷贝**（304）上，向 stdout 写 `{opsText, courses, log, n, available}`（291-317）。
- 每个 op 的全部知识是一条 `REG` 记录（52-267）：`need` 必填、`fields` 夹紧、`run` 执行、`say` 文案；执行器 `runOp`（280-288）只读表，不认识任何具体 op。
- 未知 op 名 → 整批拒绝（295、298-300），一条都不执行，`courses` 原样返回。
- 单文件、只 `require('fs')`、无随机无时间；同输入必得同输出，唯一副作用是 stdout。
- `n` 是各 op **自报**数量之和（309），与"实际改了几门"没有等式关系：`sort`/`stats` 恒返回 0，`swap` 返回 2，`del` 返回删除门数。

## 2. 三个最重要的不变量（每条一行，说明破坏它会怎样）

1. **「校验 → 克隆 → 执行」的三段顺序**（295 验完所有 op 名 / 304 才 `JSON.parse(JSON.stringify(...))` / 307 才开始跑）：破坏它——把校验挪进循环、或边跑边验——拒绝路径（300）返回的 `courses` 已带着前面几条 op 的改动，"整批拒绝、课表原样"变成静默的部分提交，而代码里没有任何回滚手段能补救（附带缺陷：295 用 `bad` 的**真值**判断，`op: null` 这类假值条目会穿过校验、直接在 281 抛 `TypeError`，实测 `ops:[null]` 崩在这里，未走 300 的拒绝分支）。
2. **`state` 的数组同一性**（42-47 的 `spliceIn` 原地 `length=0` 再 `push`；304 是 `const`；314 直接把它当 `out.courses`）：破坏它（改成 `return keep`、`state = state.filter(...)`、`sort` 用 `[...state].sort()`）→ `del`/`clear` 变成"日志说删了 N 门、输出里还在"，或输出原封不动的旧数组。
3. **没有任何地方保存"上一条 op 改了什么"**（唯一产物是 `state` 本身和 `log` 字符串数组；`runOp` 每 op 新建 `p={}`（282），op 之间不共享对象；`run` 只回一个数量；`swap` 的交换前时间只活在局部量 `ta`（121）；`add` 会改写 `p.course.name`（62））：破坏它（试图事后从 `log` 反推改动）→ 在 `[skip]` 行（311，不带编号）、`sort`（232 重排全表却 n=0）、`add`（名字被改写、原始名只剩在 `op` 里）三处同时失效。

## 3. 加一个新 op / 一个新行为，要改哪几处（按顺序列 文件:行号）

**A. 加一个 op**（只碰已有字段，例：`pin match flag`）

1. `impl.js:52` — 在 `REG` 里加一条 `{need, fields, run, say}`。这是唯一声明处：314 的 `available`、295 的分发校验都从它长出来；漏登记 = 该 op 名被判未知、整批拒绝。
2. `impl.js:8-16` — 只在需要新夹紧语义时才动 `COERCE`；`fields` 的值必须是这里的键名（`day/period/int/str/course/weeks/tag`）。
3. `impl.js:54` — `need` 的判定在 284，只认 `undefined`/`null` 为缺；空串 `""` 合法，会照常执行。
4. `impl.js:55` — 只有写进 `fields` 的字段才被夹紧并以 `p` 传进 `run`/`say`；**没登记的字段 `run` 拿到的是原始 `op` 值**（这就是 `match` 到处要 `COERCE.str(op.match)` 二次夹紧、`p` 里根本没有 `match` 的原因）。
5. `impl.js:56-66` / `impl.js:67-69` — `run` 返回数量（286 的 `|| 0` 会把 `undefined/null/false` 变成 0），`say` 只读 `n`/`op`/`p`，不能改 `n`。
6. `impl.js:20-32` 与 `impl.js:269-277` — **只有新 op 要读写课表里的新字段时**才必须动这两处：`normalizeCourse` 是全字段白名单（不在里面就进不了 `state`，也进不了 314 的输出）；`normalizePatch` 是 `edit` 的白名单，272-274 三个分支都不命中的键被**静默丢弃**（无 else、无报错），症状是"日志说改了 N 门、字段没变"。

**B. 加一个行为**（跨 op，或改日志与输出）

- 日志前缀只有两个拼接点：`impl.js:311`（`${log.length + 1}) ...`，`[skip]` 行走另一分支、不加编号）和 `impl.js:300`（未知 op 的日志硬编码 `1) 拒绝：...`，完全不经过 311）。要统一格式必须**两处都改**，否则同一份 `log` 里有两套编号规则。
- `impl.js:280` 的 `index` 是死参数：308 传 `log.length + 1` 进去，但 280-288 的函数体一次都没引用它。序号的语义不在 `runOp` 里。
- 输出字段有三个**独立**的 `out` 字面量：`300`（拒绝）、`302`（空 ops）、`314`（正常）。新字段要三处都加——现在 `available` 只出现在 314，另外两条路径上根本没有这个键。
- 跨 op 的累积状态现在**不存在**。两个可行落点：`286` 前后（同一处能同时看到 `state`、`op`、`p`、返回的 `n`），或 `307-312` 的循环体（能同时看到 op 下标和已累计的 `n`）。任选其一即可；选循环体意味着"上一条 op"这个知识点长在执行器里、长不到 `REG` 表上——这是这张表第一次装不下的东西。
- 做"撤销"前先钉死一个字：`[skip]` 的 op 算不算"上一条"？它在 `log` 里没有编号（311），两种读法都自圆其说。另一条不靠快照的路线是重放：`opsText`（314）就是 `JSON.stringify(ops)` 重新序列化后的 ops 全文，从 `origCourses` 重放前 N-1 条结果确定（`add` 的自动改名只依赖 `state`，59-63），代价是每条 undo 重放 O(N)。
- 做"命中次数"要知道判定散在几处：名字匹配有两份独立实现——`35` 的 `hit()`（被 86/102/118/119/133/147/161/191/208 使用）和 `75` 的 `del` 内联副本 `state.filter(c => !c.name.includes(...))`；另有三类不是名字匹配的命中：`221`（`untag` 按 `tag` 相等）、`180` 与 `246-247`（`clear`/`swapDay` 按 `day` 相等）、`58-61`（`add` 的 `taken` 用 `name ===`，且在 `while` 里反复调用，会重复计）。只在 `35` 加计数器会漏掉 `del`/`untag`/`clear`/`swapDay` 四个 op；`swap` 又对 `hit` 调了两次（118、119），不去重就双计。计数器不能塞进课程对象——`normalizeCourse`（20-32）是白名单，塞进去会直接漏进 314 的输出；改 `stats` 还要注意 257-265：`run` 把结果写进 `p._text`（260），`say` 只是把它读出来（264），`p` 同时是入参和 `run`→`say` 的数据通道。

## 4. 三处「看起来能改其实不能改」的地方（附原因）

1. **`impl.js:42-47` 的 `spliceIn` 不能改成"返回新数组/重新赋值"**：44-46 原地清空再填，是为了让 `state` 保持同一个数组对象（304 是 `const`，314 直接把它当 `out.courses`）；换成 `state = state.filter(...)` 或 `[...state].sort()` 后 `out.courses` 还是旧引用，`del`/`clear` 变成"日志成功、输出没变"。另外 43 行的 `n = list.length - keep.length` 必须在 44 行截断**之前**算，挪到后面删除数恒为 0，`say` 就会说"没找到匹配的课"。
2. **`impl.js:35` 的 `includes(COERCE.str(m))` 不能顺手收紧成 `===` / `startsWith`**：`need`（284）只拦 `undefined`/`null`，`match: ""` 是合法输入，`x.includes("")` 恒真 → 空 match 是**通配整表**的实际行为（实测 `del` + `match:""` 删光全部课，日志"删除 N 门（名字含「」）"）。改成 `===` 会让 `""` 从"整表"变成"零命中"，而 `del` 在 75 行有另一份判断、不会跟着改 → 同一个 `match` 在两个 op 上语义分裂。要改必须 35 和 75 同时改，并先确认这是契约还是巧合。
3. **`impl.js:14` 与 `impl.js:18` 的声明顺序不能"整理"**：14 行是箭头函数体，惰性引用 18 行的 `const defaultWeeks`，靠"调用晚于声明"活着；而 13 行引用的 `normalizeCourse`（20）是**函数声明**，会提升。并排两行形状一样、安全级别不一样。任何在模块初始化期就求值 `COERCE` 的改动（顶层预生成默认课、给 `REG` 预置静态默认值、把 `normalizeCourse(...)` 提到模块级常量）都会在 18 行抛 `ReferenceError: Cannot access 'defaultWeeks' before initialization`，而且只在启动时炸一次，看起来像环境问题。

## 5. 一个新人最可能在哪里理解错（你的猜测）

- **主猜：他会用浅拷贝当快照。** 做撤销最自然的一步是 `const snap = state.slice()` 或 `[...state]`，看着像"课表存下来了"；但每个 op 都在原地改同一个 course 对象（88 `Object.assign`、135 改 `name`、209 改 `tag`、246-247 改 `day`），`slice` 复制的只是引用 → 撤销后一门都没恢复，而 `courses` 看上去"没变化"，很容易被误诊成"undo 分支没被执行"。深一层也不够：`weeks` 是课程里唯一的对象字段（20-32），14 行把它原样返回给调用方、147 行 `{...c}` 只做浅拷、88 行把所有命中课指向同一个 `patch.weeks` 对象 → 连"每门课浅拷一层"都还在共享同一个 `weeks`。
- **次猜：他会把 `280` 的 `index` 当成日志序号的正规入口。** 308 传的是 `log.length + 1`，签名 `runOp(state, op, index)` 也在暗示"序号在这一层拼"；照这个理解动手，要么每条日志出现两个序号，要么把 1 基序号当 0 基下标用。真实前缀只由 311 决定，`index` 从未被读取。
