# inline：body 级内嵌横切——宏唯一可能真正赢成本的形状

## 前面所有横切实验都是"外包型"，宏没赢

审计挂在分发器外面 → 表驱动 1 处、宏 3 处、手写 4 处（per-op 全 0）。
结论：**O(1) 来自"有统一漏斗"，不来自宏。**

## 这一轮的横切是"内嵌型"

> 新需求：**每个 op 执行完，必须准确知道它改了哪些字段**，并写进 log。
> （现实里的对应物：审计哪几个字段、生成 undo 记录、同步时的字段级冲突检测）

难点在于：**这个信息必须来自 body 内部**，不能靠外面猜。

| 机制 | 怎么做 | 改 body 时会不会自动跟上 |
|---|---|---|
| **宏** | 展开时**遍历 body 的 form**，收集所有 `(setf (fld c "x") ...)` 的目标字段 | **会**——它是从 body 现算的 |
| **表** | 每个 op 在注册表里手写 `writes: ["day","periodFrom"]` | **不会**——要人去改那行 |

## 核心判据（只有一个）

**改一个 op 的 body（多写一个字段），问：声明的"改动字段集"会不会自动跟上？**

```
宏臂  → 期望 0 手改（宏重新扫 body）
表臂  → 期望 1 处手改（去改 writes 那行）
```

**这是唯一能区分"宏 vs 表"的判据。** 前面几轮测的都是"加一个 op"，那两边都 O(1)；
这一轮测的是"**改一个 op 的 body**"，形状不同。

## 三组测试

```
T1  加新 op：两边都应当 0 手改（复现前面的结论，作对照）
T2  改已有 op 的 body：多写一个字段
       宏臂 应 0 手改；表臂 应 ≥1 手改
T3  改已有 op 的 body：少写一个字段
       同上
```

判据脚本会：
1. 在 body 里插入/删除一行 `(setf (fld c "note") ...)`（CL）或 `c.note = ...`（JS）；
2. 重新生成/重新运行；
3. 检查 log 里该 op 的"改动字段集"是否包含/不包含 `note`；
4. 统计人工干预处数。

## 判据（`check-inline.cjs`）

```bash
node check-inline.cjs --dir runs/inline-cl   --lang cl
node check-inline.cjs --dir runs/inline-js   --lang js
```

- **J1** 原样：跑 3 个 op，log 里的字段集与实际变化一致
- **J2** 注入"多写 note" → 重新跑 → 字段集必须含 `note`，且**手改 0 处**
- **J3** 注入"少写 note" → 重新跑 → 字段集必须不含 `note`，且**手改 0 处**
- **J0** 判据能红：把实现换成"写死字段集"的假货，J2/J3 必须失败

## 记账

```
机制固定成本          若干行
per-op 声明成本       （两边都记）
T2 / T3 手改处数      核心
```

## 预注册

```
H1  宏臂 T2/T3 手改 = 0，表臂 ≥ 1
H2  两边机制固定成本相当（都在 50 行内）
H3  若 H1 不成立（表臂也能 0 手改），则"内嵌型横切"这个区分不成立，
    宏在任何横切形状上都不占优 —— 那就是一个干净的反证
```
