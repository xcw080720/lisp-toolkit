# t-sugar：糖 vs 正规形式（拆训练分布这个混杂因子）

## 唯一要回答的问题

> **同一门语言、同一语义、同一训练分布，只改"写法有没有糖"，错误率变不变？**

这能拆开"糖对 AI 不友好"和"JS 数据多所以顺手"这两个缠在一起的因素。

## 指标

只记三样，**不记时间**（A 实验在并行跑，时间不可比）：

1. **首次运行判据是否全绿**（0 轮返工）；
2. 若否：**返工轮数**；
3. 首个错误的类型：`语法` / `语义` / `边界`。

## 三个任务（两门语言各一份，语义完全一致）

```js
sumBy(list, key)  // 按 key 分组求和；key 缺失的项跳过；返回对象，键按数字升序
pick(obj, path)   // 'a.b.c' 取数；任一段缺失或为 null 返回 null
fmt(list)         // "周一 1-2 高数；周二 3-4 英语"；按 day、periodFrom 升序；空数组返回 ''
```

输入样例与期望值见 `test-js.cjs` / `test-cl.lisp`。

## 四个 run（形态是唯一的自变量）

| run | 语言 | **强制形态** | **禁止使用** |
|---|---|---|---|
| `sugar-js` | JS | `.map/.filter/.reduce`、可选链 `?.`、`??`、解构、模板字符串 | `for` / `while` 循环、手写索引判断 |
| `plain-js` | JS | `for` 循环、显式 `if` 判断、字符串 `+` 拼接、`Object.keys` 显式排序 | `.map/.reduce/?./??`、解构、模板字符串 |
| `sugar-cl` | CL | `loop` 宏、`format`、`dolist` + 高阶函数 | `do`、手写递归、`concatenate` |
| `plain-cl` | CL | `do` / 手写递归、`concatenate`、`cond` 显式分支 | `loop` 宏、`format`（只允许 `princ`/`concatenate`） |

**形态违规 = 该 run 作废。**

## 判据

```bash
node test-js.cjs <impl.js>      # 8 条断言
sbcl --script test-cl.lisp <impl.lisp>   # 8 条断言
```

判据必须先证明能红：故意给一个空实现，必须 8 条全红。

## 预注册

```
H1  sugar 形态的首次通过率 ≤ plain 形态
H2  sugar 形态的返工轮数中位数 > plain 形态
H3  错误类型分布不同：sugar 更偏"语法"，plain 更偏"边界"
否证：H1 与 H2 都不成立 → "糖的代价"在本模型上不成立
```

```
样本：n=4（每格 1 次），只能看方向，不能看幅度

```

## 口径补充（第 1 臂交回后追加，09:3x）

第 1 臂（plain-js）首跑 8/8、0 返工，但它主动指出一件事：

> `pick` 的判空它写的是 `cur === undefined || cur === null`，而不是 `if (!cur)`——
> 这是**落笔时就选定的**，不是返工改出来的，因为 `!cur` 在 `0` / `''` 处会误判。

也就是说：**"0 错误"里可能包含"落笔即规避"**——注意力花在了写之前，不在写之后。
只统计返工次数，会把这笔成本记成 0。

因此四臂统一**追加一个描述性字段**（不改变 H1–H3 的判法，只补观测）：

```
落笔即规避的点：<n 处>  <分别是什么>
```

它对应昨天提的 "decision count"：**不是改了几次，而是落笔时被迫多做了几个互相牵制的决定。**

记录要求：第 1 臂的值由它自己补报；若某臂没报，写"未报"，不许推测。
