# t-sugar-2：把「模型能力」补成第三维

> 上一轮（`t-sugar`）四臂零返工，结论只能是"**此能力下无差异**"，不能是"糖无害"。
> 这份规格把模型能力作为自变量补进去，其余全部沿用。

## 要回答的问题

> **糖的净成本是否随模型能力下降而上升？**
> 若上升，则"糖对那些不反人类的语法来说其实更难写"成立——只不过被大模型的能力掩盖了。

## 设计：2 × 2 × 2

```
形态   ：糖 / 正规
语言   ：JS / CL
能力   ：BIG（当前主力）/ SMALL（27B 级，通道就绪后填具体 id）
```

8 格 × **每格 2 次采样** = 16 个 run。串行、独占、每个 run 一个 fresh agent。

**降级方案**（时间不够时）：先跑 4 个关键格——`JS×糖×SMALL`、`JS×正规×SMALL`、`CL×糖×SMALL`、`CL×正规×SMALL`。
理由：大模型那 4 格已由 `t-sugar` 覆盖（全零返工），可以直接当基线引用。

## 上一轮的三处缺陷，这轮必须堵上

### 缺陷 1：禁用清单不对称（CL 被逼手写归并排序 34 行）

**改成按"语义"禁，不按语言各写一份**：

```
禁止：接收函数作为参数的库函数
  JS：map / filter / reduce / forEach / sort(fn) / ...
  CL：mapcar / remove-if / sort / funcall / uiop:split-string / ...

允许：纯语法糖（JS 的 ?. / ?? / 解构 / 模板串；CL 的 loop / format / dolist）
```

两侧规则**同语义、同粒度**，写进 prompt 时逐字一致（只换语言名）。

### 缺陷 2：判据测不到边界

上一轮的 8 条断言对"键序、稳定性、null、越界、类型混杂"零覆盖，导致 H3 无法判定。

**这轮的断言清单（冻结，共 14 条，两侧各一份）**：

| # | 断言 | 覆盖 |
|---|---|---|
| 1 | `sumBy` 基本分组求和 | 主路径 |
| 2 | `sumBy` 空数组 → 空结果 | 空 |
| 3 | `sumBy` 缺 key 跳过 | 边界 |
| 4 | `sumBy` value 非数字跳过 | 类型混杂 |
| 5 | **`sumBy` 键序：`{10:…, 2:…}` 必须按数字升序 2,10（不是字典序）** | **键序** |
| 6 | `pick` 深路径 | 主路径 |
| 7 | `pick` 中途为 null → null | 边界 |
| 8 | `pick` 不存在 → null | 边界 |
| 9 | **`pick` 值本身是 `0` / `''` 时不能当成缺失** | **假值陷阱** |
| 10 | `fmt` 排序与连接 | 主路径 |
| 11 | `fmt` 空数组 → `''` | 空 |
| 12 | **`fmt` 排序稳定性：day 相同时按 periodFrom，再相同保持输入顺序** | **稳定性** |
| 13 | **`fmt` day 越界（0 / 8）不崩，按兜底名输出** | **越界** |
| 14 | **`fmt` 单元素 / 分隔符不出现在首尾** | **拼接边界** |

**判据必须先证明能红**：空实现 14/14 全红；再给一个"键序用字典序"的错实现，第 5 条必须红。

### 缺陷 3：只记返工次数，漏掉"落笔即规避"与"为合规而写"

这轮记四列：

```
返工轮数
落笔即规避的点（写之前就避开的坑，n 处 + 分别是什么）
为合规而写的点（为满足形态清单硬加的东西，n 处）
每千 token 的错误数
```

## 预注册（跑前写死）

```
H1'  交互效应：小模型下 (糖错误 − 正规错误) > 大模型下 (糖错误 − 正规错误)
H2'  小模型下糖形态的成本更高，但代码量仍更少（经济性与正确性不同向）
H3'  错误类型随能力变化：小模型的错误更偏"语法"，大模型更偏"边界"
否证：H1' 不成立（两种能力下差值同号同量级）→ "糖的成本 ∝ 1/能力"不成立
```

# 追加：断网 + 小模型 = 两个新东西的对比

## 这一条改的是实验的**性质**，不是参数

之前四格的本质是：

```
JS  = 老黄忠（训练里见过一万遍）
CL  = 新兵蛋子（几乎没见过）
→ 测出来的是"熟练度差"，不是"语言差"
```

**小模型 + 断网**会把这两个身份拉平：

- 大模型对 JS 的先验厚到能把语法的不规则性整个吸收；
- 小模型对 JS 的先验也薄，**JS 对它同样是"新东西"**；
- 断网再切掉"临时查文档"这条外挂，两边都只能靠参数记忆。

于是对比变成：**两个新兵，一个拿规则少的枪，一个拿糖多的枪。**
这才是我们想问的那个问题。

> 断网不是为了"更严格"，是为了**把"查得到"这个免费外挂去掉**——它对 JS 和 CL 不平等地有用。

## 必须加一个前置检验：对称性检查

**跑正题之前，先证明"两个新东西"这个前提成立**，否则整轮的解读都错。

```
对同一模型、两种语言各做 3 个小任务（与正题无关）：
  1. 写一个函数：遍历数组求和
  2. 写一个函数：字符串按分隔符切分
  3. 写一个函数：按字段排序
每语言各 3 次，记：首跑正确率 / 返工轮数 / 每千 token 错误数
```

判读：

| 结果 | 说明 |
|---|---|
| 两语言首跑正确率接近（差 ≤ 10 个百分点） | **对称性成立** → 可以做正题 |
| JS 显著更顺（差 > 20 个百分点） | 对称性不成立 → 它仍是"老黄忠 vs 新兵"，正题结论要打折 |

**这条前置检验的结论必须写进报告，不许省。**

## 断网怎么落实（三种，任选其一并注明）

| 方式 | 做法 | 证据要留 |
|---|---|---|
| A 本地推理 | Ollama / llama.cpp 跑本地权重，本身无外网 | 进程与模型 id、`ss -tn` 无外连 |
| B 代理封锁 | 给被测 agent 套一个只允许本地回环的代理 | 一次故意发起的请求必须失败，贴报错 |
| C 防火墙 | 出站全禁（本机需要时临时开） | `curl example.com` 必须超时 |

**证据标准**：报告里必须贴一条"断网确实生效"的失败记录（不是口头声明）。

## 对结论形式的影响

断网 + 小模型之后，结论不再能写成"Lisp 好/不好"，只能写成：

```
在"两个都没见过"的条件下，
规则少的写法 vs 糖多的写法，错误率差 X，代码量差 Y。
```

**这正是你最初想要的那个对比**——只是我们一开始用大模型做，把前提搞丢了。
