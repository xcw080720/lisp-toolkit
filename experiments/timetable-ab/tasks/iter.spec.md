# iter：真实维护成本 —— 同一批需求变更，两臂各要几轮

## 为什么换因变量

前面所有实验的因变量都是**代码量**（行/字符）。
但今晚最硬的几条结论（T2-b 挡住测试看不见的错、REPL 抓出 fixture 碰不到的错）都指向：
**价值在"能不能看见/能不能改对"，不在"写多少"。**

这一轮量的是：**拿到一串需求变更，把它改对要几轮、碰几处、有没有把别的地方弄坏。**

## 三个需求变更（按顺序做，一次一个）

### D1 同名课自动加序号

`add` 时若已存在同名课程，新加的课名后缀 `(2)`、`(3)`…

新增不变量：连加三次同名课，`courses` 里应出现 `高数`、`高数(2)`、`高数(3)`。

### D2 `edit` 的节次一致性

`edit` 若只给了 `periodFrom` 或只给了 `periodTo`，必须保持
`periodFrom <= periodTo`（只给 `periodFrom` 时，若它大于原 `periodTo`，把 `periodTo` 抬上去）。

新增不变量：`edit` 只给 `periodFrom=9`，结果的 `periodTo` 必须 ≥ 9。

### D3 整批执行的原子性

一批 ops 里若有一个 op 因缺字段**未执行**，整批必须**照旧执行其余 op**，
但**日志里该 op 那一行必须以 `[skip]` 开头**。

新增不变量：一批 3 个 op（中间那个缺字段），`log[1]` 以 `[skip]` 开头，其余两条正常。

## 每个需求必须一起交

1. 代码改动；
2. **一条新不变量**（写进你的 verify 脚本）；
3. **证明它能红**：把对应实现改坏 → 该条必须失败 → 再改回来。

## 记什么（本实验的全部）

每个需求各记一行：

```
D<n> | 轮数=<改了几次才绿> | 改动处=<n>（逐处列出）| 新增字符=<c> | 有没有把原有判据弄红=<是/否>
```

最后再记：

```
原 20 条判据最终是否仍全绿
三个需求总共：轮数 / 改动处 / 新增字符
返工原因（如果有）：逐条写
```

## 判据

- 原有：`node ..\..\check-scale.cjs --impl impl.*` 必须 **20/20**（改完仍要全绿）
- 新增：你的 `verify.cjs` 里 3 条新不变量，全绿，且每条都能红

## 预注册

```
H1  CL 臂的总"轮数"更少            → 宏/单源结构让改需求更少试错
H2  JS 臂的"改动处"更少            → 表驱动改起来更局部
H3  两臂都至少有一次"把原有判据弄红" → 说明 20 条判据的覆盖面不足以保护增量修改
否证：两臂总轮数与改动处差异 <20% → 语言/结构在这个维度上无差别
```
