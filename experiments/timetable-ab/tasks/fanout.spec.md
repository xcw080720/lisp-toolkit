# fanout：一条声明长出 6 样东西（宏的第四层）

## 要回答的唯一问题

> **改了声明之后，需要手改几处？**
> 0 处 = 扇出成立；N 处 = 声明只是注释。

这是"复利"唯一还没被量过的那一层：收益随**产物数**增长，不随 op 数增长。

## 三臂

| 臂 | 生成机制 | 已知代价 |
|---|---|---|
| `fanout-cl` | `defop` 宏（展开期生成） | 无运行时开销 |
| `fanout-js` | 表 + 构建脚本生成器 | 要跑一次生成器 |
| `fanout-java` | **注解处理器（APT）** | 两趟编译、要 service loader |

**执行体不要求生成**——那是 body，按已测结论宏/注解都不吸收。只生成**元信息产出的那 5 样**。

## 一条声明包含什么

```json
{
  "name": "add",
  "params": ["course"],
  "text": "加「{course.name}」",
  "required": ["course.name"],
  "clamp": ["course.day:1..7"]
}
```

5 个 op：`add / del / edit / move / swap`。

## 必须长出来的 6 样

| # | 产物 | 判据 |
|---|---|---|
| 1 | **执行体**（手写，允许） | 功能对（12 条断言） |
| 2 | **确认文案** `opsText` | 输出 == 声明里的 `text` 渲染结果 |
| 3 | **参数校验** | 缺 `required` 字段时，报错文案含 op 名与该字段 |
| 4 | **schema** `schema.json` | 每个 op 的 `params`/`required` 与声明逐字一致 |
| 5 | **客户端存根** `client.js` | 每个 op 有一个函数，参数名 == 声明里的 params |
| 6 | **测试** `tests.json` | 每个 op 有一条断言样例，且全部能跑过 |

## 判据 A：静态一致性（`check-fanout.cjs`）

对 5 个 op 逐一校验 2–6 号产物与声明一致（2、4、5 号逐字比对）。

## 判据 B：**同步测试（核心）**

脚本自动做一次改动：

```
把声明里 add 的 text 从 "加「{course.name}」"
                  改成 "新增「{course.name}」"
然后：
  ① 重新运行生成（宏展开 / 跑生成器 / 重新编译）
  ② 检查 6 样产物里所有出现该文案的地方
  ③ 统计：需要人工改几处才一致
```

**必须记的数**：`手改处数`。期望 0。

**再测一次结构改动**：给 `move` 的 `params` 加一个 `"delta"`，看 schema / client / 校验 是否自动跟着变。

## 记录

```
<HH:mm:ss> | op=<名字> | 产物=<2..6> | 手写了=<行数> | 自动生成=<行数>
<HH:mm:ss> | 同步测试 | 改 text | 手改处数=<n>
<HH:mm:ss> | 同步测试 | 加 param delta | 手改处数=<n>
```

## 预注册

```
H1  三臂的"改 text 手改处数"都应为 0（扇出成立）
H2  JS 生成器臂需要额外一次构建步骤，其余两臂在编译期完成
H3  Java APT 的固定成本（约 40–80 行：Processor + service 文件）显著高于 CL 宏（约 10 行）
    但**每增加一样产物**时，APT 与宏的增量应当接近（都是"再加一个输出"）
否证：任何一臂的手改处数 > 0 → 该臂扇出不成立
```

## 铁律

- 5 个 op 的执行体允许手写，**但 2–6 号产物必须由声明生成**；
- 不许为某个 op 手工补丁产物；
- 判据必须先证明能红（把声明改掉但不动产物 → 判据必须报不一致）。
