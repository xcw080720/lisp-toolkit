1. 结论

1.1 一句话

宏不是「更省」，是「更早」和「更贴近 body」。
在"加一个 op 要多少行"上它常常输；在"能不能看见 body 内部"和"能不能在展开期拒绝"上，它至今没有对手。

1.2 四条硬结论

结论数字（口径已标）适用边界
行数不是语言属性物理行差 4.05×；非空白字符差 7.6%四个隔离 agent、同一份 30 op 规格
宏在编写成本上输JS 5933 · Java 6970 · CL 11460 字符（同一 15 op，非空白非注释）大模型 + 联网 + 同一批人
宏在展开期校验上独占关校验：重复声明 19/19 全绿；开校验：加载即失败并点名无条件（与模型大小无关）
宏与表的痛点是同一个两个不同作者、两种结构写下同一句：「这张表装得下 op，装不下时间轴」无条件（结构性质）

1.3 宏的四层账

维度谁赢证据
编写成本表驱动同一 15 op：CL 11460 vs JS 5933 字符（1.93×）
产物扇出（一条声明长 5 样）打平三臂手改都是 0；成本 JS 2058 < CL 5969 < Java APT 18328 字符

0. 一句话结论

在这个规模上，Lisp 的弱项暴露得比强项明显。 宏确实把"加一个 op"从 2–3 处压到 1 处，但为此多付的建造成本在 20 次重复以内收不回来；而 JS 靠标准库（JSON.parse）直接把体量压到 Lisp 的 40%。
时间维度的数据全部不可用（见 §6），所以本报告不回答"谁快"。

3.2 宏的边界（由实验数据反推）

  • 能吸收：按 op 的横切（校验 / 文案 / 兜底 / 失败语义 / 名册）→ 加 op 只写一条 defop。
  • 不能吸收：字段的纵切（模型→序列化→文案→日志）、跨 op 的框架层（日志聚合、整批语义、输出契约）。
  • 证据：run3x 的 4 次"改一处、另一处没跟上"全部落在后两类位置上（日志聚合 ×2、输出契约 ×1、括号 ×1），没有一次在 op 内部。

3.3 只有宏能消掉的那一处

run3m（无宏）在第 5 条自己标出：

白名单必须包含 #1 新加的 swap，否则 swap 会变成未知 op 被整批拒绝。这是整轮最险的一处耦合。

无宏实现里"已知 op 名单"是第二处必须手动同步的知识，漏掉 = 静默错误。
宏实现里名单就是 defop 注册表本身，加 op 自动进白名单。
→ 这才是"4 份副本 → 1 份"在活体实验里的复现：不是行数，是知识点数。

4. 提示能不能让 agent 想到宏？

不能，至少不能靠一句话。

两次独立采样（run3m 与它之前的评估轮）都算了同一笔账并拒绝重构：

把 apply-one / one-op-text 里每个 op 的两段 body 合并到一处，需整体搬移约 100 行，
numstat 实测 +82/−64 = 146（另一轮算 142），预算 60。
不搬行只加注册表，等于多出第三处 op 名单，重复没消灭反而更难同步。

结果：无宏 + 提示的 diff（102）只比无提示（116）少 12%。

但"从零建"时提示有效：run1m 拿到同一句暗示后，自己写了 defop DSL，338 行完成，六条隐藏用例全过。差别在于——建的时候没有既成结构要推翻。

5. 小项目是 Lisp 的弱项（本报告的核心判断）

宏的收益按重复次数计，成本按一次性预付计：

项数值
建造成本（宏版 vs 无宏版）多 3 分钟、少 132 行
每次"纯新增 op"节省2–3 处 → 1 处（约省 12–15 行）
每次"带新字段的改动"节省0（宏不覆盖字段纵切）
本项目重复次数5 条改动里只有 3 条吃到宏的好处

修正后的规律

横切成本 O(1) 的前提是"分发器已有一个统一漏斗，且它携带 per-op 元数据"。
这是架构性质。语言只决定"把这个漏斗写出来要多少行"。

我自己错了三次，方向一致

  1. "加 op 只动一处" → 归给宏，实际是单源设计（JS 表也做到）；
  2. "曲率不存在" → 归给语言，实际是分辨率不够（0.2 行/op 看不见）；
  3. "无宏是 O(N)" → 归给有无宏，实际取决于分发器有没有漏斗。

三次都是同一个错误：把设计属性读成语言属性。

追加：运行时轴 —— 宏的"零抽象开销"到底值多少

前面所有实验测的都是写代码的成本。这一轮测展开后代码跑得多快——
这是唯一能用数字回答"宏没有运行时开销"这句话的办法。

设计（同一门语言内，排除跨语言干扰）

15 个 op，同一个调用序列，三种分派机制，各自 100 万次 × 5 轮取中位：

机制形态
A 宏展开 casedefop 在编译期把 op 名摊成 case 子句 → 编译成跳转表
B hash-tablegethash 查表 + funcall
C alist 扫描assoc 线性找 + funcall

三者都在符号上分派（case 用 eql，表用 eq），保证同一起跑线。
自检：三种机制返回值都必须是 1,000,000（已通过）。

结果

机制ns/次相对
A 宏展开 case5.01.00×
B hash-table6.31.24×
C alist 扫描8.51.68×

判读

  1. "宏零开销"是真的：编译期摊平的 case 比查表快 24%，比线性扫描快 68%。
  2. 但绝对量很小：每次省 1.3 ns / 3.5 ns。100 万次才省 1.3 ms / 3.5 ms。
  3. 真实 op 的执行体比一次分派贵两个数量级（改课表、算提醒、写日志），

所以这个差异在实际业务里几乎看不见。

  1. alist 只比 case 慢 68%——线性扫描 15 个元素本来就不贵。

"为性能上哈希表"在这个规模上是个伪需求。

1. 曲线是阶梯，不是平滑上升

判据是一批一批起作用的，不是一条一条累加。
加 4 条判据而得分 0 变化的情况出现了三次（15→19、19→22、22→26）。

3. 但"前段便宜"有一半是假象

前段之所以便宜，是因为它覆盖的是判据最容易想到的东西（默认值、夹取、拒绝）。
后段贵，是因为它覆盖的是需要先知道"哪里会错"才能写出来的东西
（JSON 层的代理对、空对象、字段级语义）——而那正是变异测试的产出。

所以真正的因果关系是：变异测试让"后段判据"变得可写。
没有它，人根本想不出要测 weeks:{} 和 emoji。

必须记的口径限制

  • 样本只有 20 个变异，每杀 1 个就是 5 个百分点——分辨率粗糙，台阶是量化产物
  • 三个"0 变化"里，可能藏着"杀了 1 个但也被别的东西抵消"——20 样本看不出来
  • 要更细的曲线需要更大样本，代价是时间（CL 每变异约 0.6 秒）

一句

判据不是越多越好，是"前几条最便宜、最后几条最贵、中间那几条才是真正难想的"。
而"真正难想"的那几条，恰好只能由变异测试指出来。

附录 B：十五条测量纪律（PROTOCOL.md）

这份文件的每一条，都是被自己的数据打穿之后写下来的。

不是方法论摘抄，是病历。每条都附了它出生的那一刀。

如果你只记得一条，记第 1 条。

1. 判据先证明能红，才允许它说「通过」

来历：项目早期出过两次"假绿"——tag-untag 在 op 根本没有实现时通过了；
curv 臂的 20 个新 op 零覆盖，判据一路全绿而实际有 bug。

执行：拿一个空实现（或原样回显）跑判据，必须全红。不红就说明判据是假的，
后面所有数字都不作数。

2. 对照组必须先证明「它在相反条件下会失败」，再引用它

来历：T2-b 实验里，我写的 C3a 对照把探针注入在 (main) 之后，
结构性地必然通过——等于没证。真正让它有意义的是「注入到 main 之前」那组。

执行：任何一个"通过了"的对照，先问：它在什么情况下会失败？
答不出来，这个对照不成立。

3. 预注册的每条规则，先跑一遍边界值

来历：skillpack-repl 的 H3 写成「成立：收益 < 31%；否证：收益 ≥ 20%」。
区间 [20%, 31%) 同时满足两条。实测 23.38% 正好落进去——规则本身不可判定。

执行：写完判定规则，在纸上把几个关键值（0、阈值、区间中点）代进去跑一遍，
确认没有值同时满足"成立"和"否证"。

4. 一条检查如果「不测也知道会通过」，它就不算检查

来历：两个接手者都把"新行为是否被老判据覆盖"当成回归测试——
老判据写在需求出现之前，当然不覆盖，这是定义上必然为真。

执行：每加一条检查，先问"它能失败吗"。答案是否，就不要写。

5. 行数不是语言属性，是排版属性

来历：四个隔离 agent 写同一份 30 op 规格：
物理行 差 4.05 倍，非空白字符 只差 7.58%。
某一位把每条记录压成一行，行数从 13.9 掉到 2.1，而语言没变。

执行：

主指标 = 非空白非注释字符
参考   = 代码行 / 物理行（同语言内部才可用）
并且：数字必须带口径（见第 11 条）

6. 数据不作废，只标适用范围

来历：发现"熟练度污染"后我一度想把这些数作废。
用户的判断更对：两点的价值远大于一点，删掉一个点就没法画出能力轴。

执行：不删数，加一列"成立条件"。换条件得到的新数并列，不替换。

7. 跨条件外推必须显式声明

来历：一次"同一规格、同一判据"的实验，两臂字符比 1.076×；
另一批臂（不同天、不同作者状态）同一对比是 1.90×。方向相反。

执行：跨语言/跨模型族比较，必须同时固定：同一模型 + 同一天 + 同一份规格 + 同一句指令。
做不到就写"这是外推"。

8. 熟练度与隔离不可兼得，一次实验只能买一个

来历：要测"第 N 次写会不会更快"就得同一个 agent 连做两轮（于是 H1/H2 被串味）；
要隔离就得换人（于是 H3 测到的是作者方差，不是熟练度）。

执行：开跑前明确"这一轮买的是哪一个"，另一个写进"本实验不能回答的问题"。

9. 技能包是常设条件，不是可选优化

来历：技能包对照实测只省 13.9% 字符，但具体避免了：键序错（判据会红）、
手写名单漏（#8 会红）、ASCII 兜底 127 行变 6 行。接手者原话：

「读到那句之前，我的默认写法就是 hash-table。」

执行：对照臂开跑前先喂对应技能篇目，报告注明「本臂已读：x / y / z」，否则两组不可比。

10. 复现失败比复现成功更值得记录

来历：派一个不知内情的 agent 按复现文档盲跑。数字全对，但它挑出三处硬伤：
①「非空白字符」实际是「非空白非注释字符」（照字面算会差 473）；
② Windows 上 glob 不展开、C:\tmp 不存在；③ 判据编号里没有 #20，而 --only 对不存在的编号
静默返回 0 passed / 0 failed（exit 0）。

执行：复现文档写完后必须交给一个陌生人跑；它跑不通的地方，是最有价值的输出。

11. 任何数字必须三件套：数值 + 口径 + 单位

来历：同一个实现，一个人量 6128 字符，另一个人量 8934——差 45%，
因为一个去注释、一个不去。读者会直接判定"仓库对不上"。

执行：报数时写清"这个数是去掉注释、去掉空白之后的字符数"。
缺一件就算没写。

12. 规格里写的不变量，也必须先在「完全没实现该需求」的版本上跑，必须红

来历：relay 实验的 D4 不变量（undo 后 courses 为空、n=0）在根本没实现 undo
的版本上通过了——因为未知 op 触发整包拒绝，输出恰好同形。

执行：写进规格的每条断言，也走一遍第 1 条。

13. 断言只查语义要点，不锁定某一种实现的措辞或未定义行为

来历：连续踩三次——

✗ 「periodTo 必须等于 2」      规格只说"不得倒挂"，两臂都选抬上去
✗ 「空周日志要有『没有课』」     那是某一份实现的文案
✗ 用 match:"" 空串测"匹配全部"  语义未定义，两臂本就不同

执行：断言"提到操作 + 数量""不得倒挂""字段被写入"这类语义；
要把措辞钉死，先由规格拍板，再写判据。

14. 变异得分必须绑定抽样数与基线绿

来历：加完判据后 CL 跑出 100%——因为基线本来就有 2 条红，
任何变异都"有失败"，全被记成"杀死"。改成"按新增失败判定"后是 88%。
另外同一份代码 --max 50 得 84.0%，--max 30 得 83.3%。

执行：

地板分 ↔ 抽样数（改抽样 = 改地板 = 重测）
基线不全绿 → 拒绝计分
地板只能上调，下调必须写理由
门禁本身要先证明能红

15. 替换 / 生成之后，必须验证它真的发生了

来历：同一天内三次，动作一模一样——改工具、以为改好了、其实没改。

① 给 mutate.cjs 加 --only 透传：字符串替换没匹配上，我却打印了"已加"
   → 三次扫描全部无效，白跑 15 分钟；直到发现 k=3/5/10 分数完全一样才察觉

② 给 md2html 加"跨行加粗"收尾：写错变量名（out → 实际是 outPath），替换静默 no-op
   → 16 处  原样留在产物里

③ 改对变量名后：html 是 const，赋值直接崩，文件根本没重新生成
   而我"验证"时打印的是源码里那行——它在崩溃之前就存在

执行：

① 替换后立刻 grep 目标字符串，确认新内容在文件里
② 生成后立刻检查产物的一个必然特征（例：残留  必须为 0、行数必须变）
③ 不许拿"我打印了那段代码"当验证——那只证明文件里有这行，不证明它被执行
