语言、方案与失效的相关结构

v3 实验报告 ｜ 2026-10-31 ｜ 12 次独立生成 ｜ 判据 36 条（两语言自证能绿能红）
Common Lisp（SBCL 2.6.4）× JavaScript（Node 24）｜ 仓库：lisp-toolkit
三条结论
  1. 语言几乎不影响代码量。同方案下 JS/CL = 0.97×（内联）与 0.81×（抽象）。旧数据的 1.93× 来自「方案不对等 + JSON 生态」，不是语言。
  2. 抽象（宏 / 表驱动）省 28–40% 字符，两语言一致（CL 1.39×、JS 1.66×）。
  3. 抽象的代价是失效集中。一次通过率 内联 6/6、抽象 2/6，失败集中在同两条边界判据上。→ 符号层改变的不是错误率的均值，是错误的相关结构。

2.3 失效点

判据内容命中格数性质
#32空命令串应输出 err BADARG，实际无输出3（CL macro 全部）方案相关：宏把 15 个 op 收敛成一个生成器，空输入不属于任何 op，掉进缝里；table/inline 的 default 分支天然接住

#32 是漏（该报错没报），#36 是过量（不该报错却报）。判据必须同时约束两者，否则会奖励“过度检查”的实现。

五、T1 修正

原 T1（隐含）：符号层价值 ∝ P（执行者错误率） × D（决定数） —— 只写了收益侧。v3 补上成本侧：

inline（15 个独立分支）：错误互相独立     P(全绿) = ∏(1−pᵢ)      实测 6/6
macro/table（1 个生成器）：错误完全相关   P(全绿) = 1 − p_shared   实测 2/6
符号层净收益 = 收敛带来的节省（30–40% 字符）
             − 收敛带来的失效集中风险（从 ∏(1−pᵢ) 退化为 1−p_shared）

符号层改变的不是错误率的均值，是错误的相关结构——从 15 个独立的错，变成 1 个共享的错。

T1b（新命题）：抽象把 N 处检查收敛成 1 处；该处写对则全对，写漏则全漏。因此收益随 D 增长，风险随「该处被判据覆盖的程度」下降。推论：没有外部判据时，抽象的期望收益可能为负；有判据时为正。

七、边界（不外推）

  1. 规模：只有 15 op，规模维度完全没测。
  2. 模型：单族、强模型一档；P>0 的那一半仍未观测（C1）。
  3. 语言：只有 CL 与 JS 两种。
  4. 样本：每格 n=3，只够给方向，不够给区间。
  5. 判据覆盖：36 条抓到的错已知；没抓到的错未知（C4 未收口）。
  6. 任务形状：换成需要 I/O 的任务可能翻盘——旧数据正是反例。

八、复现

node check-v3.cjs --impl <file> --only 32,36

数据：results-v3.tsv（12 行，六字段）；每格 runs/<run>/prompt.txt、impl.*、log.txt。

省的不是语言，是收敛。收敛把 15 个可能的错，换成 1 个必须对的错。
所以符号层不是“更好”，它是把风险重新分配到一处——分配得值不值，取决于那一处有没有判据看着。
