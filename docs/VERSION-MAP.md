## 三、v1.6.4 到底是什么

**一句话：它是一次事故的说明书，不是一次内容更新。**

### 发生了什么

v1.6.0–v1.6.3 在本地各自做完并提交了 git，但**推送时漏了前三个**。结果：

```
先发出去的：v1.6.3  （record 23858014）
后来补推的：v1.6.0  （23858096）
            v1.6.1  （23858118）
            v1.6.2  （23858130）
再发一次：  v1.6.3  （23858146，让 concept DOI 指向它）
```

### 为什么必须发 v1.6.4

**因为 Zenodo 的 record id 单调递增，版本列表如实反映上传顺序。**

于是 v1.6.0 的 id（23858096）**永远大于** v1.6.3 的 id（23858014）。任何点开 Versions 列表的人，都能看出顺序不对——**而如果我没说明，他就只能自己猜。**

所以 v1.6.4 做的事是：把真实顺序、每个包怎么来的、哪部分是真的，一次讲完。

### v1.6.4 做了什么

**只做一件事：把这件事写在明面上。**

| 位置 | 内容 |
|---|---|
| record notes | 完整的 record id 对照表 + "哪些是真的、哪些是补的" |
| 包内 `docs/UPLOAD-ORDER.md` | 六行表，按真实上传顺序排 |
| 包内 `README.md` 第一行 | 一行警告，指向上面那个文件 |

**没改任何数据、没改任何判据、没改任何数字。**

### 为什么值得单独一版

因为它记录了一条规则：

> **一个会去比对 record id 的读者，本来就有权怀疑顺序被隐瞒。**
> 与其赌他不看，不如自己先讲。

这条规则的代价是发一个纯文档版；不写的代价是**整套"可审计"的说法都站不住**。
