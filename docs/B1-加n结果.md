### 1.5 判据口径（v1.6.1 起只有一个）

`check-v3.cjs` 里装着两个契约：判据 1–36 属 `tasks/v3.spec.md`（15 op），37–56 属 30-op 变体。对 15-op 实现，后者恒红，`36/56` 不是质量指标——所以本文件一律用 `--upto 36`，且**必须显式给分母**（不给直接拒绝执行）。

曾经有第二个口径：`#31`（未知命令→BADARG）、`#32`（空命令串→BADARG）在规格里没写明，被当作超纲判据剔除过。**v1.6.1 已把这两条写进 `v3.spec.md` §4.1**，因此：

| 口径 | CL · macro | CL · inline | JS · inline | JS · table |
|---|---|---|---|---|
| **v1.6.1 起（唯一口径，36 条全算）** | **1/6** | **1/6** | 6/6 | 6/6 |
| ~~v1.6.0 的"剔除口径"（已废）~~ | ~~3/6~~ | ~~2/6~~ | 6/6 | 6/6 |

**CL 合计：2/12。** v1.6.0 报的 5/12 作废——那不是"实现更好"，是规格当时少写了两行。补上之后，要求是真实要求，那 3 格（macro r3、inline r1、inline r3）算真失败。

`#36`（swap 误报 CONFLICT）曾同属超纲，`v3.spec.md` L71 现已明文覆盖，故**转正**、失败算真错（`cl-macro r1` 栽在 #16 + #36）。细节见 `reports/备忘录-CL错误分布与两口径-20261101.md`。

| 比较 | 比值 | 95% CI | 含 1.0 | 判读 |
|---|---|---|---|---|
| **A 语言 · inline**（JS/CL） | **1.008×** | **[0.829, 1.116]** | **含** | 语言不影响代码量 |

### 2.1 为什么这次的结果比 32768 轮可信

32768 轮的 B、C 不可引用，因为 CL 侧只剩"恰好没撞上限"的格，是幸存者样本（且被排除的恰恰偏长）。65536 轮 12/12 都有产物，**不再有截断筛选**；剩下的 6 格废码是"执行者写错了"，不是"工具把它掐了"。这两件事在账上必须分开——前者该算能力账，后者不该。

## 三、结论（三条，按强度排）

### 3.1 语言不是变量——现在是两个方案下都成立的结论

`A = 1.008× [0.829, 1.116]`、`B = 1.007× [0.879, 1.095]`。两个方案的区间**都跨 1.0**，且都不宽。

对照历史：可核层 0.91×（n=1）、探索层 0.97×（n=3）、32768 轮 0.988×（n=6）、65536 轮 1.008×（n=6）。四层方向一致。

**能写进论文的说法**：
> 在同规格、同判据、单轮无反馈、n=6/臂的条件下，JS 与 CL 的非空白非注释字符比在 inline 与抽象两种方案下分别为 1.008（[0.829, 1.116]）与 1.007（[0.879, 1.095]）——**不能排除相等**。

### 3.2 方案效应存在，且两种语言测出同一个数

`C = 1.200×`、`D = 1.200×`。这两个数不是凑巧对齐——它们是两条独立路径算出来的（CL 侧 n=6、JS 侧 n=6），落在同一位置。

**抽象省 17%，95% 区间 [7%, 29%]（CL）/[7%, 36%]（JS）。**

对照历史三档：

| 层 | 方案效应 | 折算 |
|---|---|---|
| 可核层（n=1） | CL 1.21× / JS 1.54× | 17% / 35% |
| 探索层（n=3） | CL 1.39× / JS 1.66× | 28% / 40% |
| **本次（n=6，两语言各 6 格）** | **CL 1.200× / JS 1.200×** | **17% / 17%** |

**"抽象省 28–40%"这个说法作废。** 现在能说的是：方向稳定、幅度 ~17%、且**两语言一致**。历史那两档偏大，最可能是模型版本不同（v3 的十二格来自更早的执行者）。

### 3.3 CL 侧执行崩塌（即使给足预算）

| | JS | CL |
|---|---|---|
| 有产物 | 12/12 | 12/12（65536 轮） |
| first_pass · 36 条口径 | **12/12** | **2/12** |
| first_pass · spec 合规口径 | **12/12** | **5/12** |
| 连加载都失败 | 0 | **6/12** |

6 个 crash 的错法分布（`analyze-cl-errors.cjs`）：

```
3 × 结构/读取期（2 × READ error during LOAD、1 × 读到文件尾＝括号不配平）
2 × 符号误用（把变量当函数调，含把 sb-ext:*posix-argv* 当函数）
1 × 其它（ERROR: 直接退出）
```

**没有一个落在"逻辑写错但能跑"这一层。** 这说明失败发生在"能不能成为可加载的产物"，而不是"写得对不对"。

预算翻倍之后，这个结论没有变软，反而更清楚：**CL 的失败不是"写长了被截断"，是"写出来加载不了"**。括号不配平、`end of file in form starting at line N`。

这条与 T1b 有关但方向要说准：它**不**支持"符号层改变错误的相关结构"；它支持的是更基础的一句——**在弱一些的执行者上，语言的门槛先于方案的收益出现**。CL 的前缀/括号语法在这一档模型上成了独立失败源，把"抽象省字"的测量整个盖住过一次（32768 轮）。
