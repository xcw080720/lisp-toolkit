# RELEASE NOTES — v1.7.2（2026-11-01，勘误）

> 只做一件事：**更正 v1.7.1 notes 里一处归因错误。**

---

## 错在哪

v1.7.1 的 notes 写着（原文）：

> “A counting trap is recorded because it nearly produced a wrong conclusion: the attack baseline (`tmp/attack-base.js`) scores 84/84 while the ten cells score 78/84, **because it is not the same code — it implements the six table-level rewrite operators the cells lack**.”

**那个 because 是编的。**

---

## 真因：一行

六个反例变异体在派生时，**都把 `String(r.verb).toLowerCase()` 改回了裸 `r.verb`**。

于是每个反例的原始分里都混着 **6 条与攻击目标无关的驼峰红**（`#37 #38 #39 #42 #43 #49`）。

- `attack-base.js` 保留着 `toLowerCase()` → **84/84**
- `runs/` 下十格没有 → **78/84**

**两者差的就是这一行，不是"两条代码线"。**

---

## 去污染控制（只还原那一行，保留攻击改动）

| 反例 | 原始分 | **去污染后** | 去污染后的红集 |
|---|---|---|---|
| `attack-copyto-noconflict` | 76/84 | **82/84** | 仅 #83、#84 |
| `attack-copyto-nodup` | 77/84 | **83/84** | 仅 #86 |
| `attack-n4` | 11/84 | 11/84 | 73 条（含 #85） |
| **`attack-leadspace`** | 78/84 | **84/84** | **空** |
| **`attack-io`** | 78/84 | **84/84** | **空** |
| **`attack-json`** | 78/84 | **84/84** | **空** |
| 上游 `attack-base.js` | 84/84 | — | 空（原版确实绿） |

---

## 结论怎么改

| 原表述 | 更正后 |
|---|---|
| 三个反例「78/84，与源实现同分」 | **「84/84 全绿」，即 v4 完全零视野** |
| 差 −6 因为「不是同一份代码」 | **差 −6 因为那处 `toLowerCase()` 污染** |

**「v4 对行首空格 / 文件 IO / JSON 零视野」这个结论不变，而且现在证据更强**：去污染后这三组在 84 条内容判据上**一条都不红**，只有 H1 / S1 / S2 能分辨。

---

## 这条错误的性质

不是判据错，不是数据错，是**归因错**：

> 看到两个数字不同，就编了一个解释，**没去查那 6 条红到底是什么**。

那 6 条是 `#37 #38 #39 #42 #43 #49` —— **全是驼峰，任何一格都能一眼看出是同一组**。我先把原因写下来了，才去核对。

**教训**：看到「分数差 N」时，**先列出差的那几条具体是哪些判据**，再解释原因。
