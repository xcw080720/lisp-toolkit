# 上传顺序声明（UPLOAD-ORDER NOTICE）

> 2026-11-01 补记。这一节只解释一件事：**v1.6.x 的发布时间戳不是真实的写作顺序。**

## 发生了什么

v1.6.0–v1.6.3 在本地已经各自做完并提交，但发布时顺序搞错了：

| 上传顺序 | record id | 版本号 | 性质 |
|---|---|---|---|
| 1 | 23858014 | v1.6.3 | **误发**（当时 1.6.0–1.6.2 还没发过） |
| 2 | 23858096 | v1.6.0 | 补发，按 git `32e96c2` 重建 |
| 3 | 23858118 | v1.6.1 | 补发，按 git `7549717` 重建 |
| 4 | 23858130 | v1.6.2 | 补发，按 git `83da03e` 重建 |
| 5 | 23858146 | v1.6.3 | 重发一次，让 concept DOI 指向它 |
| 6 | 本版 | v1.6.4 | **把上面这件事写进 notes 和 README** |

Zenodo 的 record id 单调递增，所以版本列表显示的才是真实上传顺序；版本号代表的是**写作**顺序，不是**上传**顺序。

## 什么是真的，什么是补的

**真的**：每个包的文件状态都由 `git archive` 从对应提交导出，release metadata 里的 sha256 就是那个压缩包的哈希。没有任何文件为了配合顺序而改过。

**补的**：只有 v1.6.0–v1.6.2 的**发布时间戳**。它们比它们所描述的内容晚。

**另外**：record 23858014 是 v1.6.3 的重复版本（第一次误发），应忽略，以 23858146 为准。

## 为什么写这一节

一个会去比对 record id 的读者，本来就有权怀疑顺序被隐瞒。与其赌他不看，不如自己先讲清楚。

这套数据的全部价值建立在「不信任何人，包括自己」上。既然如此，时间戳上也不该赌。
