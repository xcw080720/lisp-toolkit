`CITATION.cff` 那两个字段不是「写法不规范」，是**不该出现在 authors 里**：CFF 1.2.0 的 `definitions.person` 字段清单不含 `type` 与 `contribution`，且 `additionalProperties: false`。它们属于 `contributors` 项。

现在：`authors` 只有作者本人；新建 `contributors` 段，`type: other`，`contribution` 写清做了什么（判据工程的三个方向、盲跑复核驱动、门禁第五至七步、包构建、以及每一次自我更正的记录）。

## 四、门禁第七步：发布元数据一致性

前六步守判据、守冻结文件，**没有一步守对外声明**。于是第二节和第三节的两个错都能一路发出去。

第七步只做机械比对，不评价措辞：

| 检查 | 能抓住什么 |
|---|---|
| `CITATION.version` == `.zenodo.json.version` | 两个文件各说各话 |
| `CITATION.doi` == concept DOI | 版本 DOI 落后（v1.7.5 的错） |
| `authors` == `creators` | 作者集合漂移 |
| `contributors` == `contributors`，且非空 | 贡献者栏空着或被写进 authors |
| `notes` 与 `description` 都提到当前版本号 | **摘要停在旧版**（第二节的错） |

### 三次破坏测试

| 破坏 | 结果 |
|---|---|
| `CITATION.version` → `1.7.5` | FAIL ← `version 不一致：CITATION=1.7.5 / zenodo.json=1.7.6` |
| `CITATION.doi` → 版本 DOI `23872219` | FAIL ← `CITATION 的 doi 不是 concept DOI：10.5281/zenodo.23872219` |
| 摘掉 `description` 里的 `v1.7.6` | FAIL ← `description 里没有 v1.7.6（对外摘要停在旧版）` |

三次都还原，`CITATION.cff` 的 sha256 回到 `D31E33FA…C526`，复跑 PASS。

### 第七步的版本号检查，改了三版

**第一版**用 `String(desc).includes('v' + version)`。盲跑子代理把摘要里的一处 `v1.7.6` 改成 `v1.7.60`——**检查照样 PASS**，因为 `'v1.7.60'.includes('v1.7.6')` 为真。

**第二版**改用边界正则。**第一次又改错了**：写成 `(?<![0-9.])v1\.7\.6(?![0-9.])`，左边界连「点」一起禁了。而 notes 里的原文是

```
…not evidence.v1.7.6 (2026-11-02): …
```

版本号前面正好是句号，于是**正常文本被误判成「没有当前版本号」**，三条测试全红在同一句上——红错了地方，测试本身是假的。

改成左边界只禁数字 `(?<![0-9])v1\.7\.6(?![0-9])`，A/B/C/D 四项过了。

**但第二轮盲跑又挖出两个绿灯：**

| 洞 | 做法 | 旧版结果 |
|---|---|---|
| **B0** | 只把 description **第一处** `v1.7.6` 改成 `v1.7.60`，第二处留对 | **PASS**——读者第一眼看到的那句写错了，门禁全绿 |
| **B1** | 两边 `version` 同时写短成 `1.7` | **PASS**——版本号拼进正则当字面前缀，`v1.7` 后面是 `.`，右边界成立 |

B1 比 B0 严重：B0 是摘要笔误，B1 是**元数据里的版本号本身写少一节**，检查却因为前缀匹配放行。

**第三版**不再用正则边界，改成三件事：

1. 先校验 `version` 形如 `^\d+\.\d+\.\d+$`
2. 把 notes / description 里所有 `vX.Y[.Z]` 形式的版本号**抽出来**，判断当前版本是否精确在列表里
3. 要求 **description 的第一处版本号等于当前版本**（读者第一眼看到的那句）

### 七项验证

| 测试 | 期望 | 实际 |
|---|---|---|
| A description 里**全部** 2 处 `v1.7.6` → `v1.7.60` | FAIL | `FAIL ← description 里没有 v1.7.6；第一处版本号是 v1.7.60` |
| **B0 只改第一处** | FAIL | `FAIL ← description 第一处版本号是 v1.7.60，不是 v1.7.6` |
| **B1 两边 version 写 1.7** | FAIL | `FAIL ← version 不是三段式：1.7；description 里没有 v1.7` |
| **Z 两边 version 写 `01.7.6`** | FAIL | `FAIL ← version 不是三段式或带前导零` |
| B 作者顺序颠倒、集合相同 | PASS | PASS（旧的有序比较会误报） |
| C 一方多一个作者 | FAIL | `FAIL ← authors 与 creators 不一致：[许宸玮] vs [许宸玮、测试乙]` |
| D 全部还原 | PASS | PASS，两文件 sha256 逐字节一致 |

> 最后加的那条（前导零）是子代理 `fb41aef0` 发现的：`^\d+\.\d+\.\d+$` 会放行 `01.7.6`。改成 `^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)$` 后它才 FAIL。

> **A 第一次也做错了一次**：只替换了 description 里第一处 `v1.7.6`，第二处还在，检查仍然命中 → PASS。那是**测试没改干净**，不是判据漏判。
>
> **B0 的存在说明另一件事**：判据原来只要求「摘要里提到过当前版本」，两处里有一处对就算提到。第三版把「第一处」也算进来，是因为**读者只看开头那句**。

### 仍未覆盖的（子代理列的九条绕过）

第七步**没有外部锚点**：不读 git tag、不读 Zenodo record id、不比 `date-released`。所以两边一起停在旧版本号（比如都把 1.7.6 改成 1.7.5），检查是绿的。它也不比 `title`、`license`、`identifiers`、`abstract`、`contributors[].type` 这些字段。

最后一条当场兑现成了一个真错：`CITATION.cff` 的 abstract 里还写着 `nine surviving mutants`，而这个值描述里已声明被 C4 审计取代。**第七步不看 abstract，这句旧结论会随包一起发出去。** 本版已改掉，但检查本身仍然看不见它。

## 四之补、第八步：反例仍然能红

v1.7.5 的 notes 把「反例不在包里、门禁无法验证判据还活着」记成了下一个洞。这一版把它接上了。

`counterexamples/matrix.tsv` 记录了每个变异体让哪些判据变红。第八步**抽样四个**（首、两个三分点、尾，确定性选择），重新跑一遍，比对「现在的红集」与「记录的红集」。

判据被改弱、变异体被动过、实现被替换——红集都会变，这里会 FAIL 并指名是哪个变异体、记录的红集与现在的红集分别是什么。

| 破坏 | 结果 |
|---|---|
| 把 `matrix.tsv` 里 `add-noclash` 的红集从 `#4 #57` 改成 `#4` | FAIL ← `add-noclash（记 #4 / 现 #4 #57）` |
| 还原 | 哈希逐字节一致，复跑 PASS |

**为什么只抽样**：32 个变异体全跑约 4.5 分钟，对默认门禁太慢。抽样是确定性的，但确实只覆盖 4 个——全量复跑记在「没做什么」里。

## 五、补的实测数据（这一节不是说明文字）

### 5.1 十格基线从头复跑

原始 stdout 全部落盘在 `experiments/timetable-ab/baseline-v17/raw/`，汇总在 `results.tsv` / `results.json`。

| 结果 | 值 |
|---|---|
| 格数 | 10 |
| 总耗时 | **255.1 s** |
| 分布 | 8 格 78/84，2 格 84/84（`d1-check-macro-1`、`d1-check-macro-3`） |
| 低于地板 | **0 格** |
| 每格红集 | 恒为 `#37 #38 #39 #42 #43 #49`（驼峰 verb），逐格相同 |

**顺手纠正一个口径错误**：此前记的是「Lisp 单格 65–77 秒，全跑约 12 分钟」。实测 **Lisp 25.0–37.7 s，JS 8.1–8.2 s**，全跑 **255.1 s**。那个数字写进了 v1.7.5 的 notes，改不了，记在这里。

### 5.2 干净基线与变异体矩阵

十格里最好的实现是 84/84，但它们的判据集里带着那 6 条驼峰噪音。**反例必须从 84/84 的干净基线派生**，否则任一条红都分不清是攻击造成的还是噪音。

- `counterexamples/base-clean.js`：`full-js-inline` 改 6 处驼峰输出 → **84/84**
- `tools/mutation-matrix.cjs`：对基线逐处打补丁，每个变异体落盘为 `counterexamples/mut-*.js`，跑一遍 `check-v4`，记录它**具体让哪几条判据变红**
- 产物：`counterexamples/matrix.tsv` / `matrix.json`

**目的不是造一堆红的**，是回答一个能数的题：

> 84 条内容判据里，有多少条**在世上存在一个能让它红的实现**？

v1.7.0 时这个数是 **8/84**（新增的 #83 #84 #85 #86 + H1 H2 S1 S2）。这一轮做到 **45/84**，逐条红集见 `matrix.tsv`。

### 5.3 盲跑复核（独立子代理，从零重建）

| 项 | 结果 |
|---|---|
| 干净基线 | 复核代理**独立**判断出同样 6 处驼峰、改出**逐字节相同**的文件（sha256 `616E2E96…0AB`） |
| 前 25 个变异体 | 24 条红集一致；1 条主代理明细漏列（`add 不查 to<from` → `#33`） |
| 第二批 7 个 | **7/7 吻合** |
| 两批并集 | **45 条**，互无交集 |
| 有无「改了却全绿」的哑判据 | **没有**，32 个行为全部被至少一条抓到 |

复核代理还带回四句比数字更有用的话，全部记下、没有辩护：

1. **覆盖数对变异体口径敏感**——`trim`/`clear` 换一种改法各能多红一条（#54、#60/#75）。换个人造变异体，45 会变。
2. **`#60` `#75` 抓的是 n 的一致性，不是 `trim` 语义**——`trim` 方向改错它们照样给 `ok trim 1`。
3. **`#36` 是万能网**——三个不同变异体都红它，不能当独立鉴别信号。
4. **`#37 #38 #39` 没有任何变异体点亮**，但它们本来就有现成反例（8 个格红在驼峰上）。所以「存在能让它红的实现」的下界是 **48/84**，不是 45。

详见 [`docs/REPLICATION-v1.7.6.md`](REPLICATION-v1.7.6.md)。
