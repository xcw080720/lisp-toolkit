性质：**小项目**（单个 ops 执行器，500 行以内）。记住这一点——结论全部受它约束。

## 0. 一句话结论

**在这个规模上，Lisp 的弱项暴露得比强项明显。** 宏确实把"加一个 op"从 2–3 处压到 1 处，但为此多付的建造成本在 20 次重复以内收不回来；而 JS 靠标准库（`JSON.parse`）直接把体量压到 Lisp 的 40%。
时间维度的数据全部不可用（见 §6），所以本报告不回答"谁快"。

计时 = log 首尾时间戳；行数 = LF 字节计数。

| run | 语言 | 提示 | 墙钟 | 命令 | 失败 | public | hidden 结构 | hidden 严格 | 抄了几段 | 行数 |
|---|---|---|---|---|---|---|---|---|---|---|
| run1 | Lisp | 许可+指路 | 87 s | 11 | 4 | 3/3 | **6/6** | 2/6 | **4** | 470 |
| run1n | Lisp | 中立 | 93 s | 12 | 8 | 3/3 | 5/6 | — | 0 | 424 |
| run2 | JS | 许可+指路 | 44 s | 6 | 0 | 3/3 | **6/6** | 1/6 | 0 | 178 |
| run2n | JS | 中立 | 42 s | 8 | 1 | 3/3 | 5/6 | 0/6 | 0 | 206 |
| **run1m** | Lisp | **宏暗示** | 117 s | 12 | 4 | 3/3 | **6/6** | — | — | **338** |

四个发现：

1. **暗示确实引起抄**：Lisp 从 0 段 → 4 段；但收益几乎为零（省 6 秒、多对 1 条用例）。
2. **抄的是"缺件"，不是算法**：JSON 解析骨架、匹配语义、中文文案模板——全是标准库不给的部分。
3. **最大方差来自我的 spec**：两个中立格（Lisp 与 JS 各自独立）栽在同一条（`add` 的 `day=0` 未夹到 1），因为规格里 `edit` 写了夹取、`add` 那行没写。**同一份模糊，两种语言同等误读。**
4. **run2 满分靠结构不靠抄**：它写了一个共享的 `canonCourse` 规整函数，夹取对 `add`/`edit` 同时生效；run2n 逐 op 写就漏了。→ *一处规整 > 抄一段代码。*

### 3.1 run3x 逐条触点（本轮信息量最大的一张）

| # | 改动 | 动几处 | 宏吸收了什么 |
|---|---|---|---|
| 1 | 新增 `swap` | **1** | 缺参校验、opsText 拼接、未知 op 兜底、失败不出文案 |
| 2 | `edit` 改 `weeks` | **4** | 无——撞上"一条 op 只能出 1 条日志"的框架上限，被迫改 main |

| 5 | 未知 op 整批拒绝 | **1** | 只碰执行入口，op 内部一行没改 |

### 3.2 宏的边界（由实验数据反推）

- **能吸收**：按 op 的横切（校验 / 文案 / 兜底 / 失败语义 / 名册）→ 加 op 只写一条 `defop`。
- **不能吸收**：字段的纵切（模型→序列化→文案→日志）、跨 op 的框架层（日志聚合、整批语义、输出契约）。
- **证据**：run3x 的 4 次"改一处、另一处没跟上"**全部落在后两类位置上**（日志聚合 ×2、输出契约 ×1、括号 ×1），没有一次在 op 内部。

### 3.3 只有宏能消掉的那一处

run3m（无宏）在第 5 条自己标出：

> 白名单必须包含 #1 新加的 `swap`，否则 swap 会变成未知 op 被整批拒绝。这是整轮最险的一处耦合。

无宏实现里"已知 op 名单"是**第二处必须手动同步的知识**，漏掉 = 静默错误。
宏实现里名单就是 `defop` 注册表本身，**加 op 自动进白名单**。
→ 这才是"4 份副本 → 1 份"在活体实验里的复现：不是行数，是**知识点数**。

## 4. 提示能不能让 agent 想到宏？

**不能，至少不能靠一句话。**

两次独立采样（run3m 与它之前的评估轮）都算了同一笔账并拒绝重构：

> 把 `apply-one` / `one-op-text` 里每个 op 的两段 body 合并到一处，需整体搬移约 100 行，
> numstat 实测 **+82/−64 = 146**（另一轮算 142），预算 60。
> 不搬行只加注册表，等于**多出第三处 op 名单**，重复没消灭反而更难同步。

结果：无宏 + 提示的 diff（102）只比无提示（116）少 12%。

**但"从零建"时提示有效**：run1m 拿到同一句暗示后，自己写了 `defop` DSL，338 行完成，六条隐藏用例全过。差别在于——**建的时候没有既成结构要推翻**。

## 5. 小项目是 Lisp 的弱项（本报告的核心判断）

宏的收益按**重复次数**计，成本按**一次性预付**计：

| 项 | 数值 |
|---|---|
| 建造成本（宏版 vs 无宏版） | 多 3 分钟、少 132 行 |
| 每次"纯新增 op"节省 | 2–3 处 → 1 处（约省 12–15 行） |
| 每次"带新字段的改动"节省 | **0**（宏不覆盖字段纵切） |
| 本项目重复次数 | 5 条改动里只有 3 条吃到宏的好处 |

**结论：在 4 个 op、500 行以内、改动不到 8 条的规模上，宏的 ROE 是负的。**
转正条件（由 agent 自己给出，两次采样独立一致）：**改动 ≥ 8 条 / 单条改动要在 3 处以上落地 / op 数 ≥ 8**。

这不是"Lisp 不行"，而是**规模不匹配**：这个项目小到连复制粘贴都懒得用（run2 一段没抄），自然也小到摊不平宏的预付。

# 追加：规模臂（5 op 起建 + 连续加 10 个 op，无 diff 预算）

规则与前面不同：**不设 diff 预算、允许重写**；两边都收到等价的"单源"提示（Lisp→宏，JS→表驱动/注册表）；判据换成 19 条**不变量**（只看状态，不看文案）。

| | JS（表驱动） | Lisp（宏） |
|---|---|---|
| 建 5 op | **171 行** | 396 行 |
| 加到 15 op | **308 行** | 467 行 |
| 10 个 op 的代码增量 | **+137** | **+71** |
| 每个 op 平均 | **13.7 行** | **7.1 行** |
| 每加一个 op 动几处 | **1** | **1** |
| 不变量 | 19/19 | 19/19 |
| 回归 | 每步 1–9 恒绿 | 每步 1–9 恒绿 |

## 三个结论

1. **"1 处"不是 Lisp 的特性，是"单源"这个设计的特性。** JS 用一张 `REG` 表就拿到了同样的触点曲线（每 op 恒 1 处）。之前把"加 op 只动一处"归给宏，是错的归因。
2. **真正的差别在"每个 op 写多少行"**：Lisp 7.0 vs JS 13.7，**约 1:2**。宏把"一条声明"压得比 JS 的对象字面量更紧（字段名、校验、文案、执行体挤在一行里，不需要 `{...}` 和逗号）。
3. **交叉点不在"大项目"这种模糊说法上，是个数得出来的 op 数**：
   - 建造超支 = 396 − 171 = **225 行**
   - 每 op 省 = 13.7 − 7.1 = **6.6 行**
   - 交叉点 ≈ **34 个 op**
   - 但 Lisp 那 396 行里有约 **100 行是手写 JSON 解析器**（JS 用 `JSON.parse`，免费）。扣掉它：超支约 125 行 → 交叉点 ≈ **19 个 op**。

## 一条必须记下的隐患（两侧都有）

- **JS**：`stats` 为了不动执行器，用 `p._text` 把文案从 `run` 传给 `say`。若要求这层也类型化，第 15 个 op 就变成 **2 处**。
- **Lisp**：`sort` / `stats` 这类"不针对具体课程、只改整体"的 op，用的是 `defop` 而不是 `defop-each`——宏提供的是一条**每条课都要跑**的表单。遇到"整表操作"时，宏的抽象形状对不上，得换一张表单。

→ **单源能覆盖"每条都要做一遍"的横切，覆盖不了"整表操作"和"框架层语义"。** 这一点在两种语言里都成立。

## 检查器修正

`tag-untag` 原本一条用例里连做 tag+untag，在"未知 op 整批拒绝"路径下会**假绿**（课表原样、`tag` 为 undefined 也算过）。已拆成 `tag`、`untag` 两条独立不变量，两侧重跑均 **19/19**。

| 项 | agent 自报 | 本报告（LF/净增量） | 差异原因 |
|---|---|---|---|
| Lisp 终行数 | 467 | 467 | 一致 |
| Lisp 每 op | 7.8 | 7.1 | agent 把收尾的 +1/−1 修正也算进分母 |

## 两条只有这一轮才看得见的缺陷

1. **假绿（两种语言都踩到）**：`#15 tag-untag` 在 op 尚未实现时就通过——未知 op 触发整批拒绝，课表原样 + 日志 1 条，恰好满足断言。
   → **"不变量绿"只证明回归安全，不证明功能存在。** 已拆成 `tag` / `untag` 两条。
2. **契约缺口（我的 spec 欠约束）**：空 `ops` 时输出 `courses:null` / `log:null` 还是 `[]`，规格没写。
   Lisp 侧自查发现并修掉（+1/−1）；JS 侧恰好输出 `[]`。**这是我第三次在同一类地方漏写契约。**

## 这列数字能说和不能说的

**能说**：
- 建：JS 3.6×，改：JS 1.8×；
- 两种语言在"改"上的时间差（76 秒）远小于"建"上的时间差（78 秒）——**规模越大，建的优势越不值钱**；
- Lisp 的 287 行（活体版）与 JS 的 205 行，差距 40%，这个差距**全部来自手写 JSON 读写**，不是语言本身。

**不能说**：
- 样本各 1 次，方差未知。之前同臂重跑的墙钟方差曾达 3.5 倍（157 vs 549 秒），这次的 30/108/120 也可能有同量级误差；
- 这仍是"这个模型 + 这套提示"的数字，不是语言的理论速度。

## 时钟对齐后的第四条限制

所有计时都来自**日志里的命令时间戳**。agent 在两行命令之间写代码、读文件、思考的时间**不在其中**。
证据：`time-js-build` 的首条日志 19:14:27、首次全绿 19:14:34，间隔 7 秒——不可能凭空写出 205 行，说明整份实现是在**第一条被记录的命令之前**完成的。

→ 所以这些秒数是**下界**，而且两侧的"漏记比例"不同（JS 一次性成文，Lisp 分多轮试错，后者漏记更多）。**比率可以看，绝对值不能当真。**
## 计时协议 v2（下一轮起强制）

本轮所有秒数为**命令跨度（下界）**，不含写码与思考时间。下一轮起，每个 run 必须留三个时间戳：

- **T0** 收到任务 / 开始读规格
- **T1** `impl.*` 首次落盘
- **T2** 判据首次全绿

派生三个口径，报数时写明用哪个：**命令跨度**（T0↔末条命令）/ **到全绿**（T0→T2，含写码）/ **纯写码**（T1→T2，即返工成本）。

| 比较 | 行数差 |
|---|---|
| JS 自己有库 vs 无库 | 205 → 267 = **+62** |

| JS 有库 vs Lisp 脚本版：205 vs 414 | **+209** |

- JS 手写 JSON：68 秒
- Lisp 活体版：202 秒

1. **Lisp 侧的 202 秒包含自建活体驱动**（`live.mjs` + `q.mjs`，把 form 送进常驻 SBCL），JS 侧没有这步；
2. **脚本版多出的 127 行 ASCII 兜底**，也来自"没活体可问"的绕行。

所以正确说法是：

> 行数差基本消失（209 → 20）；时间差仍在，但**时间差里有相当一部分是"在 Lisp 里搭观测工具"的成本**，而这件事 JS 不需要——它的运行时状态本来就是可直接读的。

## 对原命题的修正

原来的说法："Lisp 输给 JS。"
现在的说法：**"Lisp 输给 JSON.parse"，剩下的 20 行与 3 倍时间，才是语言与观测工具的账。**

# 追加：曲率实验（curv-lisp）

基线 467 行（15 op，19/19），加 20 个 op 分四层，每步记录 LF 行数。

## 逐层增量

| 层 | 类型 | 序列（本步新增行） | 稳态边际 |
|---|---|---|---|
| L1 | 纯横切 `mark1..5` | 11, 3, 3, 3, 3 | **3 行/op** |
| L2 | 组合两个已有 op `pair1..5` | 19, 2, 2, 2, 2 | **2 行/op** |
| L3 | 组合上一层 `triple1..5` | 4, 2, 2, 2, 2 | **2 行/op** |
| L4 | 参数化批处理 `bulk1..5` | 9, 2, 2, 2, 2 | **2 行/op** |

每层第一个 op 都贵（11/19/4/9）——那是一次性基建：L1 补 `note` 槽、L2 写 `defop-chain` 组合器、L4 写 `defop-bulk` 宏。
**去掉每层首个之后，稳态全部是 2 行/op，不随层深变贵。**

总计 +79 行 / 20 op = **3.95 行/op**，比上一轮 scale 臂的 7.1 行/op 低 44%。

## 三个读数

1. **同层内没有曲率**：5 个点的序列是 2,2,2,2,2（L2/L3/L4），分辨率足够判死"恒定"。
2. **曲率出现在"维度"上，不在"数量"上**：每新增一种**组合方式**（层），付 9–19 行一次性基建，之后该维度下所有 op 都是 2 行。
3. **组合深度免费**：L3（triple = pair + mark）与 L2 同为 2 行/op，说明叠一层不会更贵——这是本轮唯一像"复利"的东西。

> 修正后的模型：**收益来自新增维度，不来自新增数量。**
> 加第 21 个 op 不会更便宜；加一种新的组合方式才会。

## 方法论失误（第三次假绿）

19 条判据对新增的 20 个 op **零覆盖**。agent 自己发现 `sub-op` 误用 `list*`（运行时报 "is not a string designator"），而 19/19 依然全绿。

→ **本轮"全程无回归"只证明老功能没坏，不证明新 op 对。**
→ 与之前 `tag-untag` 在 op 未实现时通过是同一个病：**判据没有随被测面扩展**。

## 两笔要单列的成本

- `mark1` 那 11 行里 **9 行是补数据模型**（新增 `note` 槽），不算语言的每-op 成本；
- `bulk5` 的 K=5 越过 `mark1..4` 上界，与 `bulk4` 等价（已在 log 注明）。

# 追加：横切关注点实验（audit）——复利真的存在，但不属于宏

需求：给**每一个 op** 加审计记录（`audit:[{op,n}]`）。三臂同一份需求、同一个判据（`check-audit.cjs`，每 op 单独跑一次；跑前已验证三个基线全红，无假绿）。

| 臂 | op 数 | 基线 | **改动处数** | 净增行 | 每 op 处数 | audit 判据 | 回归 |
|---|---|---|---|---|---|---|---|
| **Lisp 宏**（`defop`） | 15 | 467 | **3** | +3 | **0.2** | 17/17 | 19/19 |
| **JS 表驱动**（`REG`） | 15 | 308 | **1** | +6（代码 3） | **0.07** | 17/17 | 19/19 |
| **Lisp 无宏**（手写 `cond`） | 5 | 548 | **5** | +15 | **1.0** | 7/7 | 9/9 |

## 三个读数

1. **横切成本确实与 N 解耦**：宏 3 处、表 1 处，都不随 op 数增长；无宏版是每 op 一处（O(N)）。
   → 你那个"多次函数"在**这一维**上成立：`f` 定义一次，作用在 N 个对象上。
2. **但宏不是最优**：JS 表驱动 1 处 < 宏 3 处。
3. **原因在抽象的边界**：宏版把分发层拆成三个函数（`run-all` / `emit` / `main`），审计要穿过签名链 → 3 处；JS 版只有一个循环 + 一个出参 → 1 处。

## 新的一条规律（本轮真正的产出）

> **横切成本 = 这道关注点要穿过几层接口**，与"有没有宏"无关。

- 宏把「op 内部」的知识消掉了，但**新增了「分发层接口」**；横切落在 op 外部，就得穿过这层接口。
- 表驱动把声明和执行放在同一层，横切只穿一层。

所以"复利"是**架构属性**，不是语言属性。这是第四次同一结论：
触点 1:1（scale 臂）→ 组合深度免费（curv 臂）→ 横切 O(1)（audit 臂），三次都属于**单源设计**，三次都不属于宏。
## 更正：无宏臂不是 O(N)——我的预测错了

`audit-nomacro` 的真实结果是 **0 处 per-op**。它的 5 处改动是：

| # | 位置 | 内容 | 行数 |
|---|---|---|---|
| P1 | `run` L489 | 加 `audit` 累加器 | +1 |
| P2 | L494–497 | 已知名单加 `sort`（**检查器适配，非审计能力**） | +3 |
| P3 | L509–516 | 整批拒绝分支输出单条 | +7 |
| P4 | L521–524 | `dolist` 内 `push` 一条 | +3 |
| P5 | L537–538 | 输出加 `audit` 键 | +1 |

**审计本体 4 处 / +12 行；op 分支一行没动。**

它自己的解释比我准：

> 分界线不是有宏/无宏，而是**分发器是否已把 per-op 计数作为返回值带出来**。
> `apply-one` 的第二返回值本来就是"生效条数 k"，`run` 的 `dolist` 是所有 op 的必经漏斗——审计只是把已有的 k 抄一份。

## 所以三臂在"审计"这一维全部是 O(1)

| 臂 | 审计插入点 | 是否随 op 数增长 |
|---|---|---|
| Lisp 宏 | 3（`run-all`/`emit`/`main` 签名链） | 否 |
| JS 表驱动 | 1（循环 + 出参） | 否 |
| Lisp 无宏 | 4（`run` 内漏斗） | 否 |

**"O(1) vs O(N)" 这个对比没有出现。** 宏省的是**声明成本**，不是**接入成本**。

## 修正后的规律

> **横切成本 O(1) 的前提是"分发器已有一个统一漏斗，且它携带 per-op 元数据"。**
> 这是架构性质。语言只决定"把这个漏斗写出来要多少行"。

## 我自己错了三次，方向一致

1. "加 op 只动一处" → 归给宏，实际是单源设计（JS 表也做到）；
2. "曲率不存在" → 归给语言，实际是分辨率不够（0.2 行/op 看不见）；
3. "无宏是 O(N)" → 归给有无宏，实际取决于分发器有没有漏斗。

三次都是同一个错误：**把设计属性读成语言属性**。

## 检查器缺陷（我的）

`check-audit.cjs` 的 `order-3` 硬编码 `[del, add, sort]`，5-op 臂没有 `sort` → 整批拒绝 → 该条永远红。
无宏臂为守"不改 checker"的规矩，把 `sort` 登记进已知名单（P2 那 3 行）让 `order-3` 变绿——**这 3 行是适配，不是审计**，行数里已单列。
正确修法：`order-3` 应只使用被测臂真实拥有的 op。

## Java 为什么没吃亏（它的自陈 + 我的判读）

- **现代 Java 的糖真在生效**：箭头 `switch`（16 case）、`instanceof` 模式匹配（18 处，14 处带绑定变量）、`Set.of`。
  它自报：模式匹配把"判类型 + 强转"合成一步，**省了 14 段 if+cast**；箭头 switch 省 break 与 fallthrough。
- **JSON 读只要 74 行**：`Files.readString` + 手写 parser + switch 分派，比自己管字节流的 Rust（246）省一半以上。
- **异构 map + 少量强转**就够了——`Map<String,Object>` + 4 处强转，比 `enum V{...}`（Rust 10 行）更省。

> "静态类型 + 语法糖"这套组合在这个任务形状上**不收费**。

第七次同一教训：**语言血统预测不了成本，任务形状和库的有无才能。**

# 追加：产物扇出实验（fanout）——复利真的存在，但门槛是"手要不要动"

判据 `check-fanout.cjs` 共 17 条，核心两条是**同步测试**：
改声明后重跑生成，产物必须自动跟着变。

| 臂 | 生成器行数（固定成本） | 每样产物增量 | 同步 A 手改 | 同步 B 手改 | 判据 |
|---|---|---|---|---|---|
| CL 宏 | **229** | 待报 | **0** | **0** | 17/17 |
| JS 生成器 | **69** | **+4 行** | **0** | **0** | 17/17 |
| Java APT | 进行中 | — | — | — | — |

## 三个读数

1. **扇出成立**：两臂都是"改声明，手不用动"。这是本实验唯一真想要的数，不是行数。
2. **CL 的固定成本是 JS 的 3.3 倍（229 vs 69）**。
   原因不是宏慢，是 **CL 又得手写一遍 JSON reader**——`decls.json` 是外部输入，
   宏只负责展开，读不了 JSON。**缺件的账又一次盖过语法优势。**
3. **每样产物的增量是常数**：JS 实测 +4 行（1 行 builder + 1 行注册表 + 注释），
   且第 6 样产物**没有任何"记得去别处加一句"的隐性触点**。
   → **增量与 op 数无关，只与产物数线性相关。这才是"复利"的准确定义。**

## 一条只有 JS 会遇到的摩擦（新发现）

`with` 是 JavaScript 保留字。`swap` 的形参在声明里叫 `with`，
生成 `client.js` 时 `function swap(match, with)` **是语法错误**（`node --check` 直接挂）。

JS 臂的解法：自动降级为 `with$`，上一行注释保留声明原名，args 用字符串键 `{"with": with$}` 还原。

> **CL 宏里不存在这个问题**：宏展开出来的是符号，叫 `with` 也无所谓。
> 这揭示了一条生成器的隐性成本：**只要产物是"另一种语言的源文本"，声明里的名字就必须可映射为合法标识符**。
> 宏生成 Lisp 代码时不受此约束，生成别家语言时同样受限。

## 判据的两个弱点（我的）

1. **text 一致性只比前两个字符**（`slice(0,2)`），太松；agent 主动指出它"天然通过"。
   正确做法：解析渲染结果逐字比对，而不是前缀。
2. 判据会 `JSON.stringify` 重排 `decls.json`，臂只能把判据跑在副本目录里。
   应当只读。
## 更正两条（CL 臂交回后）

### 更正 1：我上一条判断错了

我写："**CL 宏没有这个问题**——展开出来的是符号，叫 `with` 也无所谓。"

**错。** CL 臂生成的是 **JavaScript 源文本**，同样撞墙：

```

```

> 保留字摩擦属于**目标语言**，不属于生成器的语言。
> 宏生成 Lisp 代码时不受限，生成别家语言时一样受限——CL 没有豁免权。

### 更正 2：我的判据漏了一条本该有的检查

原判据只看 `client.js` 里"有没有出现 op 名"，**从不解析它**。于是：

```
按原判据：JS 17/17，CL 17/17   ← 但 CL 的 client.js 是语法坏文件
补 node --check 后：JS 18/18，CL 17/18（那条红：function swap(match, with)）
```

已把 `client.js 必须过 node --check` 加进判据。**这是判据缺陷，不是臂的错**——

# 追加：T2-b —— 宏能挡住测试挡不住的东西（今晚唯一不受模型参数污染的结论）

## 命题

> 存在一种错误：**19 条判据全绿，但代码是错的**。宏能不能在**展开期**把它拦住？

## 做法

给 `defop` 加**展开期校验**（校验写在宏展开器里，不在运行时）：同名重复 / 未知字段 /
缺 `:text` / 空 body / 空名字。净新增 **84 行**，op body 一行未动。

对照组的设计是关键：

```
probe-duplicate 不是"抄一份像的"，而是"重放同一份源"
  defop 展开时把 (need text body) 源码存进 *op-sources*
  探针把它们重新拼成同一个 defop → 同一个展开 → 行为不可能不一致
```

## 四组对照（我独立复核过，不经过判据脚本）

把重复声明插到 **`(main)` 之前**，让它真正生效：

| 组 | 条件 | 结果 |
|---|---|---|
| **C3a** | 关校验（`T2B_VALIDATE=0`） | 加载 status=0，**`check-scale` 19/19 全绿** |
| **C3b** | 开校验 | 加载 **status=1**，报错 `duplicate op name "add"`，且 **stdout 为空** |

`stdout` 为空是"展开期"最硬的证据：**错误发生在任何 op 执行之前**。

另一组（尾部注入）与它互为交叉验证；四种非法声明各自被拒，报错都点名
（`unknown field "notARealField"`、`missing :text`、`has empty body`、`empty op name ""`）。
未注入时 19/19 无误伤。

## 结论

> **宏能挡住一个测试挡不住的东西。**
> 这个价值不在"更省"，在"**更早**"——它把一类错误从运行时/测试期挪到了展开期。

而它只在**成对对照**下才成立：C3a 证明错误真实存在且不可见，C3b 证明宏把它拦住了。
单独引用 C3b 什么都证明不了。

## 这一条的适用范围

**无条件成立。** 它不依赖模型大小、不依赖联网、不依赖排版：
"能否在展开期拒绝非法声明"是能力问题，不是成本问题。

→ 也就是说：**在我今晚所有"仅限大模型条件"的结论里，只有这一条可以直接引用。**

## 我的判据第五次假绿（同类）

`check-t2b.cjs` 的 C3a 把探针注入在文件**末尾**，也就是 `(main)` 之后——
第二份声明即使 body 是垃圾，19/19 也照样成立。**那一组是结构性地必然通过，等于没证。**

真正让实验成立的是"注入到 `main` 之前"那组，由实现方主动补上、我另外独立复跑确认。

这是今晚**第五次**同一形状的错误：**把"能通过"当成"证明了"**。
已固化成协议条款：**任何对照组，必须先证明"它在相反条件下会失败"，再引用它。**

# 追加：inline 实验 —— 宏第一次在成本上赢，同时挖出 JS 基线一个真 bug

## 需求（内嵌型横切，前面所有横切实验都没碰过）

| 判据 | CL 宏 | JS 表 |
|---|---|---|

| 合计 | **4/4** | **2/4** |

**这是今晚宏第一次在成本上赢，而且赢在"声明成本 = 0"上。**

## 顺带挖出的真 bug（不是实验设计的问题）

同一个输入 `edit set {day:3, periodFrom:5, periodTo:6}`：

```

```

**而 18 条判据全绿**——因为 #5 只测了 `set {day:9}` 的夹取，**从没测过 edit 改节次**。

已补第 19 条 `edit-periods-applied`（测 day + periodFrom + periodTo 三项都生效）。
补完后：CL 活体 20/20、**JS 表 19/20（#19 红）**、CL 脚本 #19 也过。

> 这是今晚**第三次**"判据盲区导致静默错"：`tag-untag`、`curv 的 20 个 op`、现在这条。
> 而且这次连**日志都在撒谎**——它报的键和实际改的键不一致。

## 宏这条路的天花板（实现方实测，如实记）

**抓得到**：`push` 到字段、动态字段名、lambda 内的写入、`incf/decf/rotatef/shiftf/psetf`。

**抓不到**：
- helper 函数里的 `(setf (course-day c) 9)` —— body 里只写 `(bump-day c)`，**log 报 `-`，实际 day=9**；

- 集合级变更（`setf *courses*`、sort、del、clear）不进字段集，这 4 个 op 恒 `-`。

> **天花板 = "这个 op 的所有字段写入都发生在它自己的 body 里"。**
> 一旦绕出 body，推导退化成静默漏报——好在 v2 的真值对照会把它判红，不会混过去。

# 追加：运行时轴 —— 宏的"零抽象开销"到底值多少

前面所有实验测的都是**写代码的成本**。这一轮测**展开后代码跑得多快**——
这是唯一能用数字回答"宏没有运行时开销"这句话的办法。

## 设计（同一门语言内，排除跨语言干扰）

15 个 op，同一个调用序列，三种分派机制，各自 100 万次 × 5 轮取中位：

| 机制 | 形态 |
|---|---|
| **A 宏展开 case** | `defop` 在编译期把 op 名摊成 `case` 子句 → 编译成跳转表 |
| B hash-table | `gethash` 查表 + `funcall` |
| C alist 扫描 | `assoc` 线性找 + `funcall` |

三者都在**符号**上分派（`case` 用 `eql`，表用 `eq`），保证同一起跑线。
自检：三种机制返回值都必须是 1,000,000（已通过）。

## 结果

| 机制 | ns/次 | 相对 |
|---|---|---|
| **A 宏展开 case** | **5.0** | 1.00× |
| B hash-table | 6.3 | 1.24× |
| C alist 扫描 | 8.5 | 1.68× |

## 判读

1. **"宏零开销"是真的**：编译期摊平的 `case` 比查表快 24%，比线性扫描快 68%。
2. **但绝对量很小**：每次省 1.3 ns / 3.5 ns。100 万次才省 1.3 ms / 3.5 ms。
3. **真实 op 的执行体比一次分派贵两个数量级**（改课表、算提醒、写日志），
   所以这个差异在实际业务里几乎看不见。
4. **alist 只比 case 慢 68%**——线性扫描 15 个元素本来就不贵。
   "为性能上哈希表"在这个规模上是个伪需求。

## 这条的适用范围

**无条件。** 它是运行时属性，不依赖模型大小、不依赖联网、不依赖排版。
和 T2-b（展开期校验）一样，属于今晚可以直接引用的硬结论。

## 一句总结今晚的四层账

| 维度 | 谁赢 | 是否受模型参数影响 |
|---|---|---|
| 编写成本（行数/触点） | 表驱动赢或打平 | **受影响**（熟练度） |
| 产物扇出（改声明手改几处） | 打平（都 0 手改） | 不受（结构性质） |
| body 级内嵌横切 | **宏赢**（0 声明 vs 15 行声明 + 1 处手改） | 不受（结构性质） |
| 展开期校验 | **宏独占**（测试看不见的错误只有它挡得住） | 不受（能力性质） |
| 运行时开销 | **宏赢 24%–68%**，但绝对量 1.3–3.5 ns | 不受（运行时属性） |

# 追加：t2a —— 宏生成宏（二阶 DSL）：单宏已经够用，二阶买的是"改动半径"

## 两臂

| 臂 | 机制 | 终局 | 净增 | 引擎改动 |
|---|---|---|---|---|
| **S 单宏** | 一个 `defop` | 606 行 / 24 op | +139 | 宏体槽位 **0**、分支 **0**；执行层 11 行（只付一次） |
| **F 宏生成宏** | `defop-family` 生一族宏 | 631 行 / 24 op | +164 | `defop-family` 本体 24 行；引擎改 **1 次 / +2 行**；结果通道 5 行 |

两臂判据全绿：`check-scale` 20/20、`verify` 9/9、`red` 9/9。
F 臂另有 `diff-legacy` 14/14（老 15 个 op 行为逐字节不变）。

## 关键发现一：单宏根本不用改

S 臂加三种形状（整表 / 只读统计 / 返回集合），**`defop` 上槽位 0 个、分支 0 个，已有 15 个声明改动 0 行**。

原因很结构性：`defop` 的槽位是 `:need` / `:text` + **任意 body**。
**只要 body 自由，它天生吃得下任意形状**——二阶 DSL 的卖点（加形状不碰宏体）在这个任务上不存在。

## 关键发现二：H1 成立与否取决于口径

| 口径 | S 单宏（每形状首次） | F 二阶（每形状首次） | H1（F ≤ S/2） |
|---|---|---|---|
| **结构化返回**（`results:[{op,value}]`） | 45 / 22 / 23 行 | **12 / 9 / 11 行** | **成立**（约 1/3） |
| **最小实现**（数字只写进日志） | **9** / 22 / 23 行 | 12 / 9 / 11 行 | **不成立**（B 形状 F 更贵） |

差异的来源是 S 臂在形状 B 自愿加了 28 行"参数化排序"（硬编码只需 9 行）。
**两个数都保留**，读者自己判断哪个更接近他的场景。

## 关键发现三：H3 命中，天花板是"数据契约"

形状 D 要**返回集合**。两臂都躲不开：都得在宏之外开一条 result 通道
（S：11 行；F：5 行 + 2 处）。

> **无论一个宏、一族宏、还是一张表，都要在某个地方处理"这个 op 要返回东西"，而且只付一次。**
> 这是抽象层级之上的共同天花板。

## 关键发现四：我的规格前提错了（重要）

F 臂用 `probe-shapes` 实测：**原 15 个 op 里只有 4 个（rename/trim/shift/tag）属于"形状 A"，
其余 11 个的 body 已经各写各的（RAW）**。

也就是说：`defop` 当初统一的只是**登记面**（字段校验 + 取值），**不是 body 形状**。

> 这解释了为什么前 15 个 op 上宏没省到钱：**它统一的那一层本来就不贵**。
> 我写规格时假设"15 个 op 是同一种形状"，这个假设在 body 层是错的。

## 最终判读

```
行数        ：二阶 DSL 更贵（631 vs 606，+25 行）
每形状增量  ：二阶 DSL 更省（12/9/11 vs 45/22/23，或 vs 9/22/23）
改动半径    ：二阶 DSL 更小（引擎 2 行 vs 单宏每次形状都碰执行层）
天花板      ：一样，都是数据契约
```

> **二阶 DSL 买的不是行数，是"改动半径"——加形状只追加一条 7–15 行的隔离声明，
> 24 个 op 与引擎不动。但每形状仍要付一条声明，所以收益要随"每形状的 op 数"增长才回本。**

**在本实验的规模（3 op/形状）上：大致打平。**

# 【重要】行数口径作废声明与替代指标

交叉实验（`reports/timetable-ab-crossover-20261024.md`）用四个**隔离上下文**的 agent、
同一份 30 op 规格、同一套 30 条判据，量了三种口径：

| 实现 | 物理行/op | 非空非注释行/op | **非空白字符/op** |
|---|---|---|---|
| 正式轮 CL | 8.50 | 6.50 | **244.20** |
| 正式轮 JS | **2.10** | **1.00** | **227.00** |
| 轮 2 CL | 12.10 | 10.10 | 381.20 |
| 轮 2 JS | 7.30 | 6.30 | 216.30 |

```
物理行差 4.05 倍
非空白字符差 7.58%
```

## 结论

> **行数不是语言属性，是排版属性。**
> JS 那位把每条 REG 压成一行，行数立刻从 13.9 掉到 2.1——语言没变，手变了。

## 本报告中受影响、必须重新标注的数字

| 位置 | 原数 | 现在怎么读 |
|---|---|---|
| 六语言行数表（205/267/277/287/439/563） | 行数 | **含排版差**，不可跨语言直接比；只能同语言内部比 |
| 每 op 边际 "Lisp 2–7 行 vs JS 13.7 行" | 行数 | **作废**；改用非空白字符，实测 CL 244 vs JS 227（差 7.6%） |
| 交叉点 19–34 | 由行数推出 | **作废**；行数变排版就变，交叉点跟着变 |
| 扇出固定成本 69 / 229 / 754 行 | 行数 | 同一作者同日写成，**可比性尚可**，但仍应附字符数复核 |
| t-sugar 30/64、41/72 行 | 行数 | 同上，同语言同任务，方向可用，幅度待字符数复核 |

## 替代指标（从现在起默认用这个）

```
首选：非空白字符/op      （人写多少东西，与排版无关）
次选：非空非注释行/op    （半独立于排版）
参考：物理行/op          （只用于同语言内部，或明确标注"含排版"）
```

## 配套的两处协议修正（来自同一份报告）

1. **N\* 公式写反了**：`(建_JS − 建_CL) / (c_js − c_cl)` 只在 `c_js > c_cl` 时给正数；
   样本一翻方向就得到"落进 10–30"的假阳性。判读时必须先看分母符号。
2. **H3 与"隔离上下文"不可兼得**：要测熟练度就得同一 agent 连做两轮（H1/H2 被串味）；
   要隔离就得换人（H3 变成作者方差）。**一次实验只能选一个。**

# 追加：用字符重算六语言成本表（去掉注释与空白）

`metric.cjs`：剥注释 → 去空白 → 数字符。三个口径同时给。

## 5 个 op（同一份 `scale.spec.md`，可直接横向比）

| 臂 | 物理行 | 代码行 | **字符** | 字符 vs JS+库 |
|---|---|---|---|---|
| JS + 标准库 | 206 | 163 | **4952** | 1.00× |
| JS 手写 JSON | 268 | 250 | 6044 | 1.22× |
| **Java** | 278 | 245 | **6970** | 1.41× |

| Rust | 564 | 537 | **9390** | 1.90× |

**排序没变，但幅度变了**：按行 CL 是 JS 的 2.01×，按字符是 **1.82×**。

## 15 个 op（CL vs JS 表驱动）

| 臂 | 物理行 | 代码行 | 字符 | 行比 | **字符比** |
|---|---|---|---|---|---|
| CL（`scale-lisp`） | 468 | 395 | **11289** | 1.51× | **1.90×** |
| JS（`scale-js`） | 310 | 272 | **5933** | 1.00× | 1.00× |

**这里字符比反而比行比更大。** 为什么？JS 那份被压成了 19 字符/行（很挤），
行数少但字符没少；CL 那份 24 字符/行。所以**行数低估了 JS 的真实体量**。

## 与交叉实验的差别（关键）

| 场景 | 行比 | 字符比 |
|---|---|---|
| 交叉实验（30 op，**同一模型、同一天、同一指令**） | 4.05× | **1.076×** |
| 本报告的 15 op 臂（**不同天、不同作者状态**） | 1.51× | **1.90×** |

两边方向相反。说明：

> **字符数比行数稳，但也不是纯语言属性——它还带着"作者当天的写法风格"。**
> 交叉实验那 7.6% 之所以干净，是因为两边**同一模型、同一天、同一句指令**。

## 因此修正尺子的使用规则

```
要比较语言  → 必须同时固定：同一模型 + 同一天 + 同一份规格 + 同一句指令
             指标用「非空白非注释字符」，行数只作参考
普通报数    → 字符 + 行 + 代码行 三个一起给，不单独引用行数
```

**本报告旧结论的新读法**：

| 原结论 | 行数口径 | 字符口径 |
|---|---|---|
| CL 手写 JSON ≈100 行，全语言最省 | 100 行 | 待单独测（下一步） |
| CL 建 5 op = 287 行 vs JS 205 行 | 1.40× | **1.82×**（同一对实现） |
| CL 15 op = 468 行 vs JS 310 行 | 1.51× | **1.90×** |
| 扇出 229 / 69 / 754 行 | — | 待重测 |

**结论：CL 并没有因为"行数虚高"而被冤枉——按字符算，它比 JS 更啰嗦。**
行数作废这件事，改变的是"4 倍"那种夸张说法，不是方向。

# 追加：skillpack 实验 —— 技能包省的不是字符，是"会踩的坑"

## 结果

| 臂 | 非空白字符 | 代码行 | 物理行 | 判据 | 返工 |
|---|---|---|---|---|---|
| **A 无技能包**（`repl-g1`） | **9028** | 352 | 415 | 9/9 | — |
| **B 有技能包**（`skillpack-cl`） | **7775** | 302 | 365 | 9/9 | **1 轮**（先 0/9） |

```
字符：7775 / 9028 = 86.1%
预注册 H1（< 80%）→ 不成立
预注册 H2（首次即 9/9）→ 不成立（先 0/9，defop 形参写法错一次）
```

## 但用字符数评判技能包，是选错了因变量

B 臂自己交了一份"哪条真帮到了"的清单，全部可判定：

| 技能包里的哪一条 | 它因此做了什么 | 不做会怎样 |
|---|---|---|
| `lisp-json`：「键序必须保持输入顺序，**不要用 hash-table**」 | 对象一律走保序 alist，`weeks` 固定 `type/from/to` | 判据 #1 用 `JSON.stringify` 逐字节比，**键序错就红** |
| `lisp-defop`：「手写 `known-op-p` 名单 → 必漏」 | 整批拒绝改成对注册表 `find-if` 一次查询 | #8 未知 op 整批拒绝会漏 |
| `lisp-defop`：「手写 per-op 文案分支 → 必漏」 | 5 个 op 名只出现一次 | 文案与 op 名册不一致 |
| `lisp-macro-value`：ASCII 兜底那一节 | writer 只把输出字符转 `\uXXXX`，**6 行** | 基线臂为此付了 **127 行** |
| `lisp-macro-value`：天花板（helper 内写入宏抓不到） | 改用 `set-fld` 唯一写入口 + `equal` 比旧值 | 走宏展开期改写会留一个静默漏报 |

**它自己说得很清楚**：

> 「读到那句之前，我的默认写法就是 hash-table。」

也就是说：**这条知识在模型的经验里不存在，技能包把它补上了，并且避免了一个一定会红的错误。**

## 结论：技能包的产出是"避免的错误"，不是"省下的字符"

```
字符数能测到的：−13.9%（H1 不成立）
字符数测不到的：
  · 一个会因为键序而红的判据被提前避免
  · 一个 127 行的 ASCII 兜底被 6 行替代
  · 一个"宏抓不到 helper 写入"的天花板被绕开
```

> **技能包在冷门知识上是经验替代品。**
> 模型对 CL 的先验薄（这正是今晚"熟练度曲线 92.5→12.7"的根因），
> 技能包把别人（或自己）踩过的坑变成**写之前就知道的事**。

## 因此定的规矩

**技能包是常设条件，不是可选优化。** 以后所有 CL/JS 对照臂都先喂 `lisp-toolkit/skills/` 下的对应篇目，
并在报告里注明"本臂已读技能包：x / y / z"，否则两组不可比。

## 发现二：REPL 的产出是"看见"，不是"少写"（这轮最重要）

判据 9/9 全绿之后，REPL 还抓出**两个判据永远看不见的错**：

```
(jw (jparse "{\"a\":[2.5,1.0,1e7,…]}"))
    → 修好前输出 2.5d0（非法 JSON）——19 条 fixture 全是整数，永远不会碰到

(op-edit {match:"高数", set:{day:9, periodFrom:5}})
    → 修好前 periodTo 被静默改成 5（改了 set 之外的键）
```

> **"判据说没坏"和"REPL 说哪里坏了"是两件事。**
> 这和 T2-b 是同一个形状：**存在测试挡不住、只有"能问/能看"才发现的错误。**

## 发现三：技能包与 REPL 确实部分替代，机制看得见

SP-live 臂报告：**技能包里"ASCII `\uXXXX` 兜底（127 行）"这条它没照做**，理由是

```lisp
(stream-external-format *standard-output*)   ; REPL 一句话就查到了答案
```

技能包给的是"提前防御"（127 行兜底），REPL 给的是"当场问清"（1 次调用）。
**两者解决的是同一件事：避免绕过。** 所以一个用得越多，另一个的边际收益越小。

## 我的预注册有一个硬错误（H3）

我写的是：

```
H3 成立：收益 < 31%
H3 否证：收益 ≥ 20%
```

**区间 [20%, 31%) 同时满足两条。** 实测 23.38% 正好落进这个洞——规则本身不可判定，不是实验的问题。

修法（已写进协议）：
- 要么把否证线改成 `≥31%`（消除重叠）；
- 要么承认它是**连续量**，报"替代率"，不设二元阈值。

> 这是今晚第 **八** 次同类错误：**判据/规则自己没被检验过**。
> 新增协议条款：**预注册的每一条必须先在纸上跑一遍边界值，确认没有区间同时满足成立与否证。**

# 追加：iter —— 真实维护成本（改需求要几轮、碰几处、会不会弄坏别处）

## 因变量换了

前面所有实验测"写多少"。这一轮测**接手一个已经 20/20 的实现，改 3 个需求**。
三个需求故意分层：D1 单点行为 → D2 字段间约束 → D3 日志/执行流。

## 结果

| 臂 | D1 | D2 | D3 | 总轮数 | 改动处 | 新增字符 | 弄红原 20 条 |
|---|---|---|---|---|---|---|---|
| **CL** | 1 / 2 处 / +242 | 0（代码）+1（判据） | 1 / 2 处 / +47 | **3** | **4** | **+289**（11289→11578） | 否 |
| **JS** | 1 / 1 处 / +160 | 0 / 0 处 / +0 | 1 / 2 处 / +35 | **2** | **3** | **+195**（5933→6128） | 否 |

```

轮数：3 vs 2
改动处：4 vs 3
```

**预注册判定**：H1（CL 轮数更少）**否**；H2（JS 改动处更少）**成立**；H3（出现回归）**否**（两臂都没弄红原有判据）。

> 注意：维护成本这一局**表驱动赢**，方向和"编写成本"一致。
> 但它赢的量很小（1.48 倍字符、1 处改动），远小于编写成本阶段的差距。

## 发现一：D2 是"零改动需求"——两臂都是

规格里的 D2（`edit` 只给一端时保持 `periodFrom <= periodTo`）**两臂都早就实现了**：

- CL：`edit` 的 `periodFrom` 分支自己就把 `pto` 抬到 `pfrom`（impl.lisp:317–318）
- JS：存量 `if (c.periodTo < c.periodFrom)` 那行（impl.js:89）本来就兜住

两臂都是 **0 处改动、0 新增字符**。实际花的时间全在**写一条能红的不变量**上。

> **维护成本的大头不是"写代码"，是"确认它已经在、并且钉住它"。**
> 这也是为什么"轮数"这个指标两臂都低——需求本身不重，重的是判断"要不要改"。

## 发现二（本轮最重要）：两种结构的痛点撞在同一个地方

两臂的 fresh agent 各自独立地写下了同一句话，只是用词不同：

> **CL 臂**：「宏把每个 op 的知识收成一条表单，但**跨 op 的机制（日志装配、跳过标记、字段间约束）全都落在宏外面**——
> 改一次需求得同时维护宏外的两处隐式接口，而没有任何判据守着那条接口。」

> **JS 臂**：「**表管住了 op 的四种声明，却没管住 op 之间的语义**——
> 加后缀改的是 add 的写路径，真正变的是 9 个 match op 的读路径和日志契约，这两样不在任何一张表里。」

**两种结构（宏 / 表）的痛点是同一个：跨 op 的机制没有单一知识源。**
D3（`[skip]` 日志标记）在两臂都落在"宏/表之外"，都必须回到执行器里打补丁：

| 臂 | D3 的补丁位置 |
|---|---|
| CL | `run-op` 加第三返回值 ↔ `run-all` 的 `multiple-value-bind` 元数（impl.lisp:275–277 ↔ 429–436） |
| JS | `runOp` 加 `skip:true` ↔ 日志拼装加分支（impl.js:285 ↔ 310–311） |

> **这解释了为什么"加一个 op"两臂都 O(1)、而"加一个跨 op 的需求"两臂都要摸两处**：
> 单源化方案收拢的是"一个 op 的知识"，从没收拢"op 之间、op 与执行器之间"的知识。

## 发现三：我的 H3 又被两个臂各自"测试错"了一次

两个臂都把 H3 理解成"**新行为是否被原有判据覆盖**"——那是**定义上必然为真**的
（老判据写在需求出现之前，当然不覆盖）。两臂都给出了"三次改坏、原 20 条全绿"的证据，
这只能证明"新需求没被老判据保护"，不能证明"改动引入了回归"。

**H3 本意是后者：改动过程中有没有把原有行为弄坏。** 两臂的记账里都写着"弄红原 20 条 = 否"，
所以 **H3 否**。

> 这是今晚第 **九** 次同类：**判据/规则在定义上就无法失败**。
> 已并入协议条款：**一条检查如果"不测也知道会通过"，它就不算检查。**

## 更正一条臂的自述（我的复核）

JS 臂报「D1 让 `del match=高数` 由删 1 门变删 2 门」。我实测：


# 追加：变异测试 —— 给判据本身打分（把"假阳"做成研究对象）

今晚被"判据看不见的错误"咬了十一次。这一轮反过来**主动制造错误**，看判据抓不抓得住。

`mutate.cjs`：对实现做**单点变异**（翻转比较符、改常量、删一行），逐个喂给 `check-scale`。
- 变红 = **杀死**（判据看见了）
- 仍绿 = **存活**（← 真实盲区，逐条列出）

|---|---|---|---|---|
| **JS 表驱动** | 35 | 19 | 16 | **54.3%** |
| **CL 宏** | 50 | 41 | 9 | **82.0%** |

**同一套 20 条判据，对两份实现的有效性差 28 个百分点。**

## 存活变异长在哪——这才是重点

### CL 的 9 条存活，6 条在 JSON 层

```
L39  指针前进 4              L140  写 false 字面量
L60  判断数字有没有小数点      L176  字符串直通
```

**原因**：20 条判据喂的都是**整数、ASCII、单层结构**。手写 JSON 层里

`edit` 的字段级语义，20 条判据几乎不覆盖（#19 只补了"三项都改"这一种赋值）。

## 两个必须记的坑（否则这个数会被误读）

**① 无效变异率是工具假象，不是语言属性**

```
JS：60 个抽样里 25 个语法无效（42%）
CL：50 个抽样里 0 个语法无效
```

原因：我的变异规则在 JS 上容易打断语法（`===`→`!==` 碰上表达式、删行删在表达式中间），
而 Lisp 是括号结构，删一行通常仍能被读入。**这是变异器的粗糙，不是"CL 更抗改"。**

**② 两个得分不能直接比"代码质量"**

它们比的是**"同一批判据对两份实现的有效性"**。
CL 得分高，是因为它的存活变异集中在**判据不喂的输入类型**（JSON 层），
而不是因为它的业务逻辑被判据覆盖得更全。

### 第六步：修掉 CL 的两个真 bug（基线回绿）

## 三个观察

### 1. 曲线是**阶梯**，不是平滑上升

判据是**一批一批起作用**的，不是一条一条累加。
加 4 条判据而得分 0 变化的情况出现了三次（15→19、19→22、22→26）。

### 2. 边际效率掉到约 1/6

| 段 | 判据数 | 字符成本 | JS 得分 | 每 100 字符买到 |
|---|---|---|---|---|
| 前段（#1–#19 + 骨架） | 19 | 7398 | 35.7% | **0.48 个百分点** |
| 后段（#21–#36） | 16 | 8830 | 35.7% → 42.9% | **0.08 个百分点** |

**后 17 条判据的成本花得比前 19 条还多，只买到 7.2 个百分点。**

### 3. 但"前段便宜"有一半是假象

前段之所以便宜，是因为它覆盖的是**判据最容易想到的东西**（默认值、夹取、拒绝）。
后段贵，是因为它覆盖的是**需要先知道"哪里会错"才能写出来的东西**
（JSON 层的代理对、空对象、字段级语义）——而那正是变异测试的产出。

> **所以真正的因果关系是：变异测试让"后段判据"变得可写。**
> 没有它，人根本想不出要测 `weeks:{}` 和 emoji。

## 必须记的口径限制

- **样本只有 20 个变异**，每杀 1 个就是 5 个百分点——**分辨率粗糙，台阶是量化产物**
- 三个"0 变化"里，可能藏着"杀了 1 个但也被别的东西抵消"——20 样本看不出来
- 要更细的曲线需要更大样本，代价是时间（CL 每变异约 0.6 秒）

## 一句

> **判据不是越多越好，是"前几条最便宜、最后几条最贵、中间那几条才是真正难想的"。**
> 而"真正难想"的那几条，恰好只能由变异测试指出来。

## 结果二：我这轮又种错一个病人（第 19 次同类）

`diag-cl-p2` 本意种「返回值丢弃」：


但替换时少开一个括号、留了闭括号 → 实际种出的是**括号失衡**。

（而它顺带指出：原实现 `aset` 的 append 分支确实没写回 `(cdr o)`，是真 bug，
只是现有键都预置了所以判据测不到——这才是我想种的那件事。）

## 结果三：盲编码裁决 —— **② 跨语言串台这一类站不住**

| 缺陷 | 医生自报 | 盲编码 A | 盲编码 B | 采信（两盲一致才采信） |
|---|---|---|---|---|
| cl-p1 日志编号 | ③ | ③ | ③ | **③ 逻辑** |
| js-p1 日志编号 | ③ | ③ | ③ | **③ 逻辑** |
| cl-p3 `loop on` | ① | ① | ① | **① 不熟练** |
| js-p3 `for-in` | ② | ① | ① | **① 不熟练**（覆盖医生） |
| js-p2 `push(keep)` | ① | ③ | ② | **不可判**（三方全不一致） |

**最终分布：① ×2、③ ×2、② ×0、不可判 ×1。**

### 为什么 ② 一次都没被采信

② 的判据是「这个写法在另一门语言里是对的」，但**举哪门语言当参照，答案就变**：

```
js-p2（push(keep)）：
  参照 Python/Java/Lisp  → 它们的 append/add/push 也不摊平 → 不成立 → ①
  参照 Perl              → push @list, @keep 会摊平        → 成立  → ②
```

**两门参照语言给出相反答案。** 所以 ② 不是"事实"，是"选择"。

### 修正：三分法应退成二分

```
保留：① 语言特有 ←→ ③ 语言无关     （两盲一致率 4/4）
废弃：② 跨语言串台                  （不可独立判定，容易变成事后解释）
```

## 结果四（这一轮最值钱的一条）

**两处 ① 全是"遍历关键字的语义选错"：**

```
CL：loop for (k . v) in  →  写成 on
JS：for (const [k,v] of …) →  写成 for…in
```

**结构上完全同类。** 也就是说：

> **Lisp 没有独有的"难"，它只是把"遍历语义"这门功课换了一套关键字。**
> JS 也有同一门课，只是名字不同。

而两处 ③ 是**同一个 off-by-one 在两种语言里的同构复现**——这反而是"语言无关"的证明。

## 结论

```
排障速度：不可判定（区间重叠；且计时起点有缺陷）
归因三分法：② 不可独立判定，应退成二分
Lisp 甜区在排障上：没有证据
但有一件事成立：两门语言最难的都是"遍历语义"，不是宏、不是括号
```

## 这条推翻的是**我的实验设计**，不是语言结论

本项目 **11 个 CL 臂，全部用 `sbcl --script`**。
而 `--script` 恰恰是不触发批处理诊断的那个入口。

> **CL 的"一次改完"能力存在，但我从来没有让任何一个 agent 用过它。**

之前所有"CL 排障没有优势"的观察，**都是在这个被关掉开关的工作流下得到的**。
那不是语言的性质，是**我的 harness 的性质**。

# 追加：**静态检查的价值 ∝ 执行者的错误率**（今天所有零结果的统一解释）

## 一、缺陷的三层可见性

| 层 | 定义 | 今天的真实实例 | 数据 |
|---|---|---|---|
| **① 立刻响** | 写下去就被点名，没跑就知道 | CL `compile-file` 对三处未定义函数 | 点名 **3/3**，附汇总 `caught 4 STYLE-WARNING` |
| **② 迟早响** | 跑到那条路径才炸 | 同一份代码走 `sbcl --script` | 点名 **1/3** 即终止 |
| | | JS `spliceIn` 改名 | `node --check` 报 **0**，运行到才 `ReferenceError` |
| **③ 永远不响** | 跑得起来、结果错、测试不覆盖 | JS `periodTo = max(from+1, …)` | 判据全绿，**没人发现** |
| | | `#4 del-miss` 假绿 | `keep` 为空时 `push([])` 长度恰好 1，断言只看长度 |

## 二、公式

```
一条缺陷的期望成本 = P(该模型写出它) × 发现时延

发现时延：① ≈ 0    ② ≈ 1 轮    ③ = ∞

静态检查节省的成本 = Σ_{可提升类型} P × (原时延 − 0)
                   ∝ 执行者的错误率 P
```

**这条式子把"语言好不好"和"谁来写"绑在了一起。**
之前所有实验都只报了语言，没报 P，所以结论互相矛盾。

## 三、天花板效应：今天五个零结果，同一个原因

| 零结果 | 表面原因 | 真原因 |
|---|---|---|
| 技能包无效（A/B 6 run） | 文档没用 | **P≈0，降无可降** |
| 第 8 篇无效 | 那篇写得不好 | 同上 |
| CL 排障无优势 | 语言没优势 | **工作流关了开关（`--script`）+ P≈0** |
| 排障时间不可判定 | 样本太少 | **六个医生全部零试错，没有可测的方差** |
| 字符数差 ≤12% | 效应小 | 作者方差 > 干预效应 |

> **今天测的不是"Lisp 有没有优势"，
> 是"在一个几乎不犯错的执行者身上，任何降低错误的干预有没有用"。**
> 答案当然是没有。

## 四、推论 A：**小参数 / 高幻觉场景下，CL 相对 JS 的优势会被放大**

机制（默认配置下，不加任何额外工具）：

```
CL   的静态名字检查在编译器里 → 默认开
JS   / Python 的在 linter / 类型器里 → 默认关（要装、要配、要跑）
```

所以一个错误率高的执行者：

```
在 CL 里  →  多出的错误有相当一部分落在 ① 层，写完即被点名
在 JS 里  →  同样多出的错误落到 ②③ 层，靠输入覆盖去撞，或者永远不报
```

**边界必须说清**：给 JS 配好 eslint / mypy 之后，这条差距会缩小甚至消失。
所以这是**「默认工具链配置下的优势」，不是「语言本体的优势」**——
它同时也告诉你**怎么抵消它**（给 JS 配 linter）。

## 五、推论 B：这是**用本地小模型的技术理由**，不只是省钱

```
① 模型越小 → P 越高 → 静态检查的投资回报越高（公式左侧的乘数变大）
② 静态检查是零推理成本的护栏（编译器不烧 token）
③ 高 P 意味着更多修复轮次；每一轮在 API 上是重新计费，在本地是电费
```

所以两条路线在成本结构上完全不同：

```
大模型 + 弱静态检查  =  用 token 买「不犯错」
小模型 + 强静态检查  =  用编译器买「犯错立刻知道」
```

**前者每次对话都付费，后者一次性配置就永久有效。**

这个论证不需要"Lisp 更好"就能成立；Lisp 只是**默认就把护栏焊在编译器里**的那一方。

## 六、可证伪预测（写死，允许被推翻）

同一份实验，换成高幻觉率的模型（Seed / Gemini 这一栏）重跑：

```
① 返工轮数从 0–1 拉大到 2–5
② ②③ 层缺陷占比上升
③ CL 的「提前响」变成可见的时间差
```

**如果换模型后轮数仍然拉不开，这条理论就错了。** 那才是真正的反证。

## 七、方法学后果（写进纪律）

```
旧指标：为了让效应不被截断，最强模型也必须 ≥1 次返工
新指标：执行者的错误率必须落在「能被测出来」的区间

→ 零返工不是好结果，是坏信号：说明这次实验没有信息量
```

**以后每一次零结果，第一件事不是找解释，是先问：P 是不是已经贴地板了。**

# 追加：C++ 臂 —— ①层最强的是它，不是 Lisp

## 七语言体积（5 op，非空白非注释字符）

| 语言 | 字符 | JSON 通道 |
|---|---|---|
| Python（有库） | **4750** | 0 行（标准库） |
| JS（有库） | 5933 | 0 行 |
| Java（无库） | 6970 | 手写 |
| Julia（无库） | 7316 | 手写（267 行） |
| CL（有库？无库 + 技能包） | 7506 | 手写 |
| Rust（无库） | 9390 | 手写 |
| **C++（无库）** | **11374** | **手写 242 行（49.6%）** |

**C++ 比 Rust 还多 1984 字符。**
「Lisp 笨重」这个指控到此彻底失去区分度——**最笨重的是 C++，而没人说 C++ 不该用。**

## 而 C++ 的业务代码是最短的

```
手写 JSON（值模型 40 + 解析器 133 + 序列化 47 + 输出装配 22） = 242 行（49.6%）
5 个 op + 小工具 + main 调度                              = 219 行（44.9%）
其中 5 个 op 本身只有 146 行 —— 比任何一臂都短
```

**强类型把业务代码压到最短，代价全在缺件上。**
结论：**缺件成本 242 行 ≈ 业务成本 219 行的 1.1 倍**。这条与之前"缺件是主要成本"的判断一致，但首次量到了 C++ 的极端值。

## ①层（立刻响）能力排序：g++ 第一

| 入口 | 一次能点名几处 | 备注 |
|---|---|---|
| **g++** | **10/10，30/30** | 语义错**不互相阻断**：第 8 行缺分号报完后，后面 9 个函数照样逐个查 |
| CL `compile-file` | 3/3 | 未定义函数/变量（STYLE-WARNING 级） |
| CL `--script` | 1/3 | 撞到第一个就终止 |
| JS `node --check` | 0/3（未定义名字） | 只做语法解析 |
| Python `py_compile` | 0/3（未定义名字） | 同上 |

**g++ 唯一会停的情况**：词法/预处理 fatal（未闭合注释）→ 只报 1 条。

> **所以「把 ②③ 提升到 ①」这件事，C++ 默认配置下做得比 CL 更好。**
> 差别在于：C++ 靠**类型系统**，CL 靠**名字检查**（未声明类型就查不到类型错）。
>
> 这修正了上一节的表述：不是"Lisp 的静态检查最强"，是
> **「有静态检查的强于没有的；有类型的强于只有名字检查的」**。
> Lisp 的位置是"无类型声明也能查名字"——比 JS/Python 强，比 C++ 弱。

## C++ 在 Windows 上的隐性成本（必须进脚注）

首个错误不是编译错，是运行期 `exit=-1073741515`（`0xC0000135 STATUS_DLL_NOT_FOUND`）。

```
MinGW 动态链接 libstdc++ / libgcc / libwinpthread
判据把 exe 编到 %TEMP% 再 spawn → exe 目录不在 PATH → 找不到 DLL
判据的编译命令写死，塞不进 -static
解法：把 mingw64\bin 前置进 PATH，源码一行未改
```

**这条成本与语言无关，与平台有关。** 记账时不能算进"C++ 更贵"。
