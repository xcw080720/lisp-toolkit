# v3 实验报告：语言、方案与失效的相关结构

> 2026-10-31 ｜ 12 次独立生成 ｜ 判据 36 条（两语言自证能绿能红）
> 本报告取代 `timetable-ab-完整报告.md` 的结论部分；旧报告保留为"设计演化"记录，其 1.93× 结论已撤回。

---

## 摘要

三条：

1. **语言几乎不影响代码量。** 同方案下 JS/CL = 0.97×（内联）与 0.81×（抽象）。旧数据的 1.93× 来自"方案不对等 + JSON 生态"，不是语言。
2. **抽象（宏 / 表驱动）省 28–40% 字符**，两语言一致（CL 1.39×、JS 1.66×）。
3. **抽象的代价是失效集中**：一次通过率 inline 6/6、抽象 2/6，且失败集中在同两条边界判据上。
   → **符号层改变的不是错误率的均值，是错误的相关结构。**

## 一、实验设置

| 项 | 值 |
|---|---|
| 任务 | 课表 ops 执行器，**固定 15 个 op**，`tasks/v3.spec.md` |
| 输入 | 命令行参数（每条命令一个 argv 项） |
| 输出 | stdout 纯文本：每条命令一行 `ok <verb> <n>` / `err <CODE>`，末尾 `#state` + 每课一行 |
| **禁止** | JSON、序列化、文件 I/O、第三方库 |
| 判据 | `check-v3.cjs`，**36 条**，完整输出行比对 |
| 设计 | 2 语言 × 2 方案 × **3 次独立生成** = 12 格 |
| 独立性 | 每格一个**新会话**、逐字同提示、不干预、全档留存（`prompt.txt` + `impl.*` + `log.txt`） |
| CL 运行时 | WSL Kali 内 `SBCL 2.6.4`（Windows 侧无 SBCL，见 `REPRODUCE.md`） |
| JS 运行时 | Node.js v24 |

四臂：

| 臂 | 语言 | 方案 | 定义 |
|---|---|---|---|
| A1–3 | Common Lisp | macro | 每个 op 一条表单；校验/文案/日志/分发由宏生成 |
| B1–3 | Common Lisp | inline | 每个 op 手写独立分支，不共用任何生成机制 |
| C1–3 | JavaScript | table | 一张注册表描述所有 op，执行器读表分发 |
| D1–3 | JavaScript | inline | 同 inline 定义 |

## 二、结果

### 2.1 总表（chars = 非空白非注释字符，主指标）

| 组 | r1 | r2 | r3 | 均值 | sd | CV | first_pass |
|---|---|---|---|---|---|---|---|
| CL · macro | 5565 N | 3836 N | 4378 N | **4593** | 884 | **19.3%** | **0 / 3** |
| CL · inline | 6490 Y | 5850 Y | 6819 Y | **6386** | 493 | 7.7% | **3 / 3** |
| JS · table | 4364 N | 3487 Y | 3340 Y | **3730** | 554 | 14.8% | **2 / 3** |
| JS · inline | 5975 Y | 5718 Y | 6927 Y | **6207** | 637 | 10.3% | **3 / 3** |

`Y/N` = 首次提交是否 36/36。CL macro r2 修复后 3916 → 3836。

### 2.2 效应分解

| 方向 | 对比 | 比值 |
|---|---|---|
| **语言**（同方案） | JS inline / CL inline | **0.97×** |
| **语言**（同方案） | JS table / CL macro | 0.81× |
| **方案**（同语言） | CL inline / CL macro | **1.39×** |
| **方案**（同语言） | JS inline / JS table | **1.66×** |

**方案效应（28–40%）大于语言效应（0–19%），且方向不一致。**

### 2.3 失效点

12 格中首轮未通过 4 格（失败事件 5 次）：

| 判据 | 内容 | 命中格数 | 性质 |
|---|---|---|---|
| **#32** | 空命令串 → `err BADARG`，实际无输出 | 3（CL macro 全部） | **方案相关**：宏把 15 个 op 收敛成一个生成器，空输入不属于任何 op，掉进缝里；table/inline 的 default 分支天然接住 |
| **#36** | 混合序列 L6：`swap` 期望 `ok swap 2`，实际 `err CONFLICT` | 2（CL macro r2、JS table r1） | **跨语言共有**：任务语义陷阱——对调两课时间本不会产生冲突，实现却多做了一次冲突检查 |

结论：**漏报与误报是两类不同的失效**。#32 是漏（该报错没报），#36 是过量（不该报错却报）。
判据必须同时约束两者，否则会奖励"过度检查"的实现。

## 四、与预注册假设的对照（`PROTOCOL-v3.md` §8）

| 假设 | 预测 | 实测 | 判决 |
|---|---|---|---|
| **H1** | 同 op、同方案下 CL chars > JS chars | inline 0.97×、抽象 0.81× | **被反驳** |
| **H2** | 宏/表驱动 scheme 的 chars < 内联 | 1.39×（CL）、1.66×（JS），方向反了 | **被反驳（方向相反）** |
| **H3** | first_pass 与语言无关、与方案有关 | inline 6/6 vs 抽象 2/6 | **成立** |
| **H4** | 弱执行者才产生 silent_failures | 强模型下 silent_failures = 0 | **在强模型上不可判**（转 C1） |

H2 的措辞原本写的是"宏/表驱动 < 内联"，实测是 1.39–1.66 倍（更大），因为**参考对象选错**：抽象省的是"重复"，不是"总量"。留档不改。

## 五、T1 修正（写入 `CONDITIONS.md` §五）

原 T1（隐含）：

```
符号层价值 ∝ P（执行者错误率） × D（决定数）
```

只写了收益侧。v3 补上成本侧：

```
inline（15 个独立分支）：错误互相独立     P(全绿) = ∏(1−pᵢ)      实测 6/6
macro/table（1 个生成器）：错误完全相关   P(全绿) = 1 − p_shared   实测 2/6
```

修正后：

```
符号层净收益 = 收敛带来的节省（30–40% 字符）
             − 收敛带来的失效集中风险（从 ∏(1−pᵢ) 退化为 1−p_shared）
```

新命题 **T1b**：

> 抽象把 N 处检查收敛成 1 处；该处写对则全对，写漏则全漏。
> 因此抽象的收益随 D 增长，风险随"该处被判据覆盖的程度"下降。
> 推论：**没有外部判据时，抽象的期望收益可能为负；有判据时为正。**

## 七、边界（不外推）

1. **规模**：只有 15 op。规模维度完全没测。
2. **模型**：单族、强模型一档。`P>0` 的那一半仍未观测（C1）。
3. **语言**：只有 CL 与 JS 两种，不能替所有语言下结论。
4. **样本**：每格 n=3，只够给方向，不够给区间。
5. **判据覆盖**：36 条抓到的错已知；没抓到的错未知（C4 未收口）。
6. **一次任务形状**：换任务（尤其换成需要 I/O 的）可能翻盘——旧数据正是反例。

## 九、一句

> 省的不是语言，是收敛。收敛把 15 个可能的错，换成 1 个必须对的错。
> 所以符号层不是"更好"，它是**把风险重新分配到一处**——分配得值不值，取决于那一处有没有判据看着。
