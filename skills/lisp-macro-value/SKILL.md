# SKILL: 宏到底值在哪 —— 四层账，每层都有数

**这份文档只回答一个问题：什么时候该用宏，什么时候不该。**

所有数字来自一次同规格、同判据、可复算的对照实验（Lisp / JS / Rust / Java / Julia）。
每个数字都标了它成立的边界；**跨边界引用就是外推，必须自己声明。**

---

## 一、编写成本：宏经常输

| 语言 | 建 5 个 op | 每 op 边际 |
|---|---|---|
| JS（有 `JSON.parse`） | **205 行** | 13.7 行 |
| Java（手写 JSON） | 277 行 | — |
| **Common Lisp（活体 REPL）** | **287 行** | **2–7 行** |
| Rust（std-only） | 563 行 | — |

**结论**：Lisp 的每一 op 边际最低（2–7 行 vs JS 13.7），但**建的固定成本最高**。
交叉点在 19–34 个 op（新手手感），熟练后可能落到 10–18。

> ⚠️ **边界**：这些数是在"大模型 + 联网 + 同一批人"的条件下测的。
> 换个模型/换个熟练度会变。**不要拿它当语言常数。**

## 二、产物扇出：打平，都成立

一条声明长出 5 样产物（文案 / schema / 客户端 / 测试 / 校验清单），**改声明后手改几处**：

| 机制 | 生成器行数 | 加第 6 样产物 | 手改处数 |
|---|---|---|---|
| **JS 生成器脚本** | **69** | **+4 行** | **0** |
| CL 宏 | 229（其中 88 行是手写 JSON） | +7 行 | 0 |
| Java 注解处理器（APT） | **754** | +18 行 | 0 |

**结论**：扇出成立的条件是"**统一声明源 + 生成器**"，跟语言无关。
CL 在这一局的劣势不是宏慢，是**它得再手写一遍 JSON 读器**。

> 附带发现：Java APT 最贵的地方不是那 754 行，是**静默失败**——
> 删掉 `META-INF/services` 后 javac 退出码 0、无警告、就是不生成。

## 三、body 级内嵌横切：宏赢，而且声明成本是 0

**需求**：每个 op 执行完，必须知道它这次**实际改了哪些字段**。

| 机制 | 做法 | 声明成本 | body 改了会不会自动跟上 |
|---|---|---|---|
| **宏** | 展开期把 body 里每个写入 place 改写成 `(fld obj "字段")`，运行期沿唯一通道用 `equal` 比旧值 | **0 行** | **会**（手改 0 处） |
| 表 | 每个 op 手写 `writes: [...]` | 15 行 | **不会**（手改 1 处，且初始声明就已经错了：声明 8 个，实际只改 1 个） |

**这是宏唯一在成本上赢的横切形状。** 分界线：

```
外包型横切（审计挂分发器外面） → 表驱动赢或打平，宏没有优势
内嵌型横切（信息必须来自 body） → 宏赢，且声明成本 0
```

### 宏这条路的天花板（必须知道）

**抓得到**：`setf`/`psetf`/`incf`/`decf`/`push`/`pop`/`rotatef`/`shiftf`、动态字段名、lambda 内写入。

**抓不到**：
- helper 函数里的写入（body 里只写 `(bump-day c)`）→ **静默漏报**；
- `funcall`/`apply` 间接写、`eval`/`compile` 运行期构造的写入；
- 值不变的写入（1→1）——对 undo 是对的，对"审计意图"会丢；
- 集合级变更（sort / del / clear）没有字段名可报。

> **天花板 = "这个 op 的所有写入都发生在它自己的 body 里"。**
> 绕出去就会静默错——所以**必须有真值对照**（运行前后 diff）把漏报判红。

## 四、展开期校验：宏独占

**命题**：存在一种错误，**测试全绿但代码是错的**。宏能不能在展开期拦住？

成对对照（本项目实测）：

| 组 | 条件 | 结果 |
|---|---|---|
| C3a | 关校验，静默重复声明**生效于 main 之前** | **19/19 全绿**（测试看不见） |
| C3b | 同一份重复声明，开校验 | **加载失败**并点名 `duplicate op name "add"`，且 stdout 为空（main 根本没跑） |

**结论**：宏能挡住测试挡不住的东西。价值不在"更省"，在"**更早**"。

> ⚠️ 引用这条时必须成对：**只贴 C3b 什么都证明不了**。
> 必须先证明"这个错误在关掉校验时测试看不见"。

校验本身的成本：约 **84 行**（五类：同名 / 未知字段 / 缺 `:text` / 空 body / 空名）。

## 五、运行时：宏赢，但量级很小

同一门语言、同一调用序列、100 万次 × 5 轮取中位：

| 分派机制 | ns/次 | 相对 |
|---|---|---|
| **宏展开 `case`（编译成跳转表）** | **5.0** | 1.00× |
| hash-table 查表 | 6.3 | 1.24× |
| alist 线性扫描 | 8.5 | 1.68× |

**结论**："宏零开销"是真的，但每次只省 1.3–3.5 ns；真实 op 的执行体比分派贵两个数量级，
业务里看不见。**"为性能上哈希表"在 15 个 op 的规模上是伪需求。**

## 决策清单（照着问自己）

```
1. op / 命令 / 事件类型会稳定长到 20+ 吗？        否 → 用表，不用宏
2. 新需求要"从 body 内部"拿信息吗？              是 → 宏（这是它唯一的独占成本优势）
3. 需要在编译/展开期拒绝非法声明吗？             是 → 宏（这是它唯一的能力优势）
4. 只要"一处声明长出多份产物"吗？                是 → 表 + 生成器就够，宏不占优
5. 已经有一大批手写实现，想事后改成宏？           不要。实测 retrofit +142 行，需 N>71 才回本
```

## 一句

> **宏不是"更省"，是"更早"和"更贴近 body"。**
> 在"加 op 要多少行"这件事上它常常输；在"能不能看见 body 内部"和"能不能在展开期拒绝"上，
> 它至今没有对手。
