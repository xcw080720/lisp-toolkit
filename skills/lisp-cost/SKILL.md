# SKILL: 成本模型 —— 什么时候 CL + 宏真的划算

## 一句话

**Lisp 的收益不在"写得快"，在"每次改动只动一处"。它的代价是"第一次建得慢"。**
所以问题永远不是"Lisp 好不好"，而是"这个项目有多少次改动"。

## 实测数字（同规模、同判据、同一模型）

| 语言 | 建 5 个 op | 每 op 边际 |
|---|---|---|
| JS（有 `JSON.parse`） | 205 行 / 30 秒 | 13.7 行 |
| JS（手写 JSON） | 267 行 | — |
| **CL（活体 REPL）** | **287 行** | **2–7 行** |
| CL（只跑脚本） | 414 行 | — |
| Julia（无 JSON 包） | 439 行 | — |
| Rust（std-only） | 563 行 | — |

## 交叉点公式

```
CL 总成本 = 建_CL + c_cl × N
JS 总成本 = 建_JS + 13.7 × N

N* = (建_JS − 建_CL) / (13.7 − c_cl)
```

|c_cl | N* |
|---|---|
| 12.7（新手） | 19–34 |
| 6（熟练） | **10–18** |

> **N\* 不是语言常数，是你现在这只手的函数。**

## 熟练度曲线（真实测量，同一批人连续写）

| 第几次 | 行/op |
|---|---|
| 1 | 92.5 |
| 2 | 59.5 |
| 3 | 24.5 |
| 4 | 12.7 |

**7.3 倍，且未平。** 拿第一次的数字去和"写了一万遍的 JS"比，比的是人不是语言。

## retrofit 的门槛（最贵的一种错）

把已有手写实现改成 defop DSL，实测 **+142 行**。

```
需要 N × (K − 1) > 142   （K = 每个 op 手写时分散在几处）
K = 3 → N > 71
```

**已有的 5 op 项目去做 retrofit，永远回不了本。** 要么从零建，要么不做。

## 什么时候**不要**用 CL

- op 数 < 10 且不会再长；
- 需要现成的 JSON / HTTP / 数据库驱动（缺件成本一次性但很高）；
- 团队里 0 个人会读（维护成本转移给了别人）。

## 什么时候值得用

- op / 命令 / 事件类型会稳定增长到 20+；
- 每一种类型都要长出"校验 + 文案 + 日志 + 分发 + 名册"这一套；
- 你有活体 REPL（没有的话，观测成本会吃掉一半收益：实测 127 行）。
