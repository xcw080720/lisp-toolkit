# SKILL: 交接文档怎么写才真的能被接手

**实测来源**：两个 fresh agent 各写一份交接文档（A 段），另两个 fresh agent 只看
「代码 + 文档」各实现三个新需求（B 段）。两臂都完成了，但都付出了代价。

---

## 一、先记三个数字

| 项 | CL 臂 | JS 臂 |
|---|---|---|
| 接手者首读字符 | 23919 | 15880 |
| 接手者"靠猜"处数 | **5** | **10** |
| 文档里的**实质错误** | 1 处 | 1 处 |

结论：**文档能让人把活干完，但"靠猜处数"两臂都在 5–10 之间**——
也就是说，真实交接里**必然有一部分只能靠接手人自己拍板**。

> **文档的目标不是"说全"，是"把必须拍板的地方标出来"。**

---

## 二、最危险的缺陷：写得很确定但是错的

两臂各有一处：

| 臂 | 文档原话 | 实际 |
|---|---|---|
| CL | 「日志后缀只改 `impl.lisp:436`，`i` 就是 D5 要的 `k`，**同义**」 | `k` 是 ops 下标（含被跳过的），`i` 是成功条数——**有 skip 时分叉**，照抄必红 |
| JS | 「另有三类不是名字匹配的命中：`untag` 按 tag、`clear`/`swapDay` 按 day」 | 规格要的是"被 **match** 命中"，这几个 op 没有 match——**越界统计** |

> **漏写，接手人会去读代码；写错，他会照着错的做。**
> 所以：**没验证过的因果句，宁可不写。**

对应写法：

```
✗ 「A 就是 B，同义」                    ← 断言式，读者不会去验
✓ 「A 与 B 在 [条件] 下相同；在 [另一条件] 下不同（我实测：…）」  ← 带边界
```

---

## 三、锚点必须用契约，不能用行号

CL 的接手者原话：

> 「文档给的是**行号锚点**不是**契约锚点**——我一动手，`436/429` 就变成 `447/451`，
> 后续引用全要重算。」

```
✗ 「改 impl.lisp:436」
✓ 「改"把一条 op 的结果拼成日志行"的那个函数；它在 run-all 里，是唯一出口
   （例外：未知 op 的拒绝日志在 main 的 cond 里手写，不经过它）」
```

**行号可以作为辅助，但每一条行号后面必须跟一句"这个位置在语义上是什么"。**

---

## 四、必须写进文档的两条裁决规则

B 段原话：

> 「材料最缺的不是信息量，而是两条裁决规则：**规格与文档冲突时谁优先**，
> 以及**这些行号属于哪一版**。」

模板里必须有这两节：

```markdown
## 0. 权威顺序
规格 > 本文档 > 代码注释。冲突时以规格为准；本文档与代码不一致视为本文档过期。

## 0.1 版本
本文档描述的是 <commit/时间/字符数> 时的代码。行号会漂，语义不会。
```

---

## 五、最容易漏写、但接手人一定会踩的

实测中两臂都撞上的一个坑（**CL 臂独立发现并实测**）：

> **未知 op 会让整包 ops 一条都不执行。**

后果：在"没实现新 op"的版本上跑 `[老 op, 新 op]`，结果是
`courses` 保持初始、`n=0`——**恰好与"新 op 生效并撤销"同形**。

也就是说：**不变量会假阳**。必须补一条"日志条数 + 日志内容"的断言才判得出来。

所以文档要写这类**结构性事实**：

```
· 一次输入里任何未知 op → 整包拒绝，一条都不执行
· 日志里 [skip] 的产生条件是「msg 非空 且 执行返回第三值为真」
· n 允许为负（undo 记负值合法）
· 新 op 的 fields 可以是空列表
```

---

## 六、自测不能只跑既有判据

两臂独立写下同一句话：

> 「『自测只跑 check-scale』是废话——**它对新行为零覆盖**，三条需求全做完照样 20/20。」

JS 臂补得更狠：

> 「那 20 条**不看日志文本**，我把每行格式全改了，`#9` 和 `#18` 依然绿。」

**写完代码必须自己写不变量，并且先证明它能红。** 既有判据保护的是"你没弄坏旧的"，
不保护"新的对不对"。

---

## 七、可直接抄的交接模板

```markdown
# HANDOFF

## 0. 权威顺序与版本
规格 > 本文档 > 注释。本文档对应 <日期/字符数> 的代码；行号会漂。

## 1. 这个程序在做什么（≤5 行）
## 2. 三个最重要的不变量（每条写：破坏它会怎样）
## 3. 加一个新 op / 新行为，按顺序改哪几处
   —— 每处写「语义位置」+ 行号；并写明这个位置**唯一还是有多份**
## 4. 三处「看起来能改其实不能改」的地方（附原因）
## 5. 五个交接人一定会踩的结构性事实
   （整包拒绝 / skip 的条件 / n 可为负 / 空 fields 合法 / 日志有多个出口…）
## 6. 我**不确定**的三件事
   —— 这一节最重要：把"需要接手人拍板"的地方明写出来，别装作都懂
```

> **第 6 节是这份文档唯一不可省略的创造性部分。**
> 实测两臂各自有 5–10 处必须靠猜——把它们标出来，比假装说全更有用。
